## The pipeline

```
PLAN_APPROVED
  POST /runs/{id}/model/generate                       T-502  model/v1/ (TMDL)            -> MODEL_GENERATING
MODEL_GENERATING
  POST /runs/{id}/model/measures                       T-503  DAX per measure, next ModelSpec and TMDL version
  POST /runs/{id}/model/bridges/{bridge_id}/generate   T-506  an approved bridge into the model (notebook if needed)
  POST /runs/{id}/model/validate                       T-504  Gate G4 entry in ValidationReport.json

      fail -> MODEL_FAILED -> POST /model/repair       T-505  -> MODEL_GENERATING | NEEDS_INPUT

CLI: python -m app.cli deploy model TMDL_DIR --name NAME (T-501)    python -m app.cli model generate runs/<id> (T-502)
```

## Decisions taken in this session (README "Working assumptions" table)

- **Sandbox topology:** one dedicated sandbox workspace per environment, `SANDBOX_WORKSPACE_ID` in `.env` (falls back to `FABRIC_SANDBOX_WORKSPACE_ID`).
- **Model authoring route:** deterministic TMDL files (T-502). An optional MCP writer behind the same interface was asked for but **not built**: the MCP server, its tools and its authentication were never chosen.
- **Retry limits:** 3 attempts per repair call (`max_attempts` in `config/repair_policy.yaml`) plus an earlier stop when an attempt makes no progress.
- **Derivation rules become SQL by the model:** a rule in `config/derivation_rules.yaml` is free text, so the model drafts one Spark SELECT from it (names and types only), code checks it and a notebook materializes it (T-506). The alternative (rules that carry their own SQL) was not chosen.

## Working rules that applied (keep following them)

- Hybrid orchestration: the run state machine and `RunStore` own state; LangGraph graphs only run bounded LLM loops (`dax_measure`, `repair`) and never change run state or write `RunManifest.json`.
- The LLM proposes, deterministic validators decide. No silent KPI assumptions. Data Gap instead of a fabricated calculation. Never send raw rows to the LLM: the DAX, reference-SQL and derivation prompts carry names and types only.
- Never read or print `.env` values; new settings go in `.env.example` with empty values. Deployments and notebooks go only to the sandbox workspace (the guard is inside `FabricItemsClient`).
- Per task: `/implement-task T-xxx` creates `task/T-xxx-<slug>` from an up-to-date `main`, sets the README status, implements, writes the offline script and the `MANUAL_TESTING.md` section, updates `.claude/CLAUDE.md`; then `/commit-push`, a PR, `/cleanup-branch`.
- No pytest. Offline scripts run as modules from the project root with the venv Python, for example `.venv\Scripts\python.exe -m app.manual_tests.t505_offline_checks` (the last line of a green run is `All checks passed.`). UI: `cd rayfin-ui; npm test; npm run typecheck; npm run build`.
- `.claude/MANUAL_TESTING.md` is CRLF: edit it by exact string replacement that keeps the line endings, and check `git diff --stat`.

## Gotchas learned in this session

- **The shell tool in this session turned some backslash escapes in Python source into control characters** (a `\b` in a regex became a backspace; a path `\v<n>\definition\tables` became a vertical tab and a tab). Write scripts with the Write tool instead of bash heredocs, avoid `\\` escapes in inline Python, and check with `grep -rlP '\x08|\x0b' app config .claude rayfin-ui/src`.
- Long bash heredocs with odd quoting sometimes failed to parse and did nothing; a script file avoids that.
- Use `.venv\Scripts\python.exe` (plain `python` had no packages). A tool call times out at about two minutes: run suites one per call or in the background.
- Test fixtures build on each other: `t502` (`build_spec`, `build_plan`, `build_inventory`), `t503` (`FakeLlm`, `spec_with_measures`), `t504` (`FakeItems`, `FakePbi`, `FakeSql`, `ReconLlm`), `t505` (`RepairItems`, `RepairPbi`), `t506` (`BridgeItems`, `FakeLakehouse`). `t503.FakeLlm` reads the measure name from the first line of the prompt, so keep the JSON payload first.
- The cache files keep only accepted answers, keyed by request hash; any input change (for example a new table in the inventory) is a new request. `ModelSpec` stays `approved` after DAX or a bridge is added; the DAX is approved with the model.
- The registered `TMDLModel` hash is not updated by a hand edit of the files; the review and the approvals use the live folder hash.
- Windows can refuse a rename for a moment: use `app/fsutil.py:replace_file`.
- `.claude/CLAUDE.md` documents the exact behaviour of every feature above; update it in the same branch when behaviour changes.
