## The pipeline

```
DATA_PROFILED
  POST  /runs/{id}/plan/sources      T-401  -> SourceResolution.json     (GET returns it, added in T-405)
  POST  /runs/{id}/plan/feasibility  T-402  -> Feasibility.json          a data gap moves the run to NEEDS_INPUT
  POST  /runs/{id}/plan/bridges      T-403  -> BridgeProposals.json      optional; needs_rules moves it to NEEDS_INPUT
  POST  /runs/{id}/plan              T-404  -> ModelSpec.yaml + ExecutionPlan.yaml   (GET returns them, validated again)
  PATCH /runs/{id}/plan              T-405  edit operations
  POST  /runs/{id}/gates/G3/check    T-405  Gate G3
  POST  /runs/{id}/approvals {"artifact": "ExecutionPlan", ...}   T-405  Accept -> PLAN_APPROVED
```

Every `POST` above is allowed in `DATA_PROFILED` only (`409 WRONG_STATE` otherwise). Exceptions: a decision on a bridge proposal is also allowed in `NEEDS_INPUT`, and Reject of an approved plan is allowed in `PLAN_APPROVED`. T-401 to T-404 never change the run state, except by raising a data gap (`NEEDS_INPUT`).

## Working rules that applied to every task (keep following them)

- **The model proposes, deterministic code decides.** Names a model returns that aren't in the inventory are discarded. A model never sees data: only the contract, the glossary and table and column names and types.
- **No proxy for a data gap.** A KPI the data can't support is `data_gap`; nothing is invented. No hardcoded table names in code: they live in `config/`.
- **Same inputs, same files.** Stages that use a model keep its accepted answer keyed by a hash of the request (`workflow/llm_cache.py`; `source_suggestions.json`, `feasibility_suggestions.json`). A version only grows when the content changes.
- **Config files are read on every call**, so an edit applies without restarting the API. A bad file is `500 CONFIG_ERROR` naming the file: `config/glossary.yaml` (T-401), `config/derivation_rules.yaml` (T-403), and the existing `config/conformed_sources.yaml` and `config/roles.yaml`. `.env.example` gained `FABRIC_SANDBOX_WORKSPACE_ID` (T-404, optional, empty).
- **Error codes added to `CONTRACTS.md`** (HTTP 409): `MAPPING_RULES_REQUIRED` (T-403), `NO_FEASIBLE_KPIS` (T-404).
- **A stage service is a plain function** (no LangGraph graph): none of these stages has a real loop (T-402 has one bounded retry). Route handlers in `api/runs.py` only call the services.
- **Task workflow:** `/implement-task T-xxx` creates `task/T-xxx-<slug>` from `main`, implements, runs the offline checks, updates `.claude/MANUAL_TESTING.md` and `.claude/CLAUDE.md`, and stops at `Awaiting manual test`. `/commit-push` commits and pushes. `/cleanup-branch` deletes a merged branch.

## Setup shared by all manual steps

Do this once; the per-task steps refer to it as "the setup".

1. **Environment.** Windows, Python 3.12 virtualenv in `.venv` (`.venv\Scripts\activate`), a `.env` copied from `.env.example` with the model and Entra settings filled in (never print it). ODBC Driver 18 for SQL Server is needed for the SQL endpoint.
2. **Start the API:** `uvicorn app.api.main:app --reload --port 8000` (Swagger at <http://localhost:8000/docs>).
3. **Start the UI (T-405 needs it):** `cd rayfin-ui; npm install; npm run dev`, then sign in at <http://localhost:3000>.
4. **Get a token for Swagger or curl:** sign in to the UI, press F12, open *Network*, click any request to `localhost:8000`, copy the part of the `Authorization` header after `Bearer `. In Swagger click **Authorize** and paste it. It lasts about an hour; treat it like a password.
5. **Roles:** open `config\roles.yaml` and put **your own UPN** in the role the task needs (`data_engineer` for exceptions and the inventory, `bi_engineer` for the plan and bridges, `business_owner` for the contract). Restore it afterwards with `git checkout config/roles.yaml`.
6. **Fixtures:** the bridge and date-table scenarios need the `nexora_test` schema of the sandbox Lakehouse (`fixtures/README.md`: run the Spark notebook `fixtures/create_test_tables.ipynb`). `python -m app.test_metadata_inventory nexora_test` lists it.
7. **Get a run to `DATA_PROFILED`** (the starting point of every task here):
   1. In the UI open `/runs/new`, enter a prompt (for example `Show net revenue by product and customer`), pick the workspace and Lakehouse and the schemas (`saleslt`, and `nexora_test` when the task says so), create the run.
   2. Open the run, click **Compile**, answer the blocking questions (define Net Revenue), and compile again until none is blocking.
   3. Open `/runs/{id}/contract`, check the G1 checklist, **Accept** as `business_owner`. The state is `REQUIREMENT_APPROVED`.
   4. Open `/runs/{id}/inventory`: **Harvest**, **Profile candidates**, **Analyze relationships**. If a candidate table is not conformed, approve an exception first (T-304 steps in `.claude/MANUAL_TESTING.md`). **Accept** as `data_engineer`. The state is `DATA_PROFILED`.
   5. When a task says "analyze with candidates", call `POST /runs/{id}/relationships/analyze` with a body `{"candidates": [{"from": {"table": "...", "column": "..."}, "to": {"table": "...", "column": "..."}}]}`.
8. **Clean up afterwards:** stop the API and UI, restore the config files you edited (`git checkout config/roles.yaml config/conformed_sources.yaml config/glossary.yaml config/derivation_rules.yaml`), delete the test runs' folders under `runs\`.

The offline checks need none of this (no sign-in, no network): `python -m app.manual_tests.tNNN_offline_checks`. They build on each other: `t302` -> `t303` -> `t401` -> `t402` -> `t403` -> `t404` -> `t405` import the fixtures of the earlier ones, so after changing a fixture re-run all of them.

## T-401 Entity-to-source mapping and conformed-table resolver

**Spec:** FR-009, §8.4, business rule 5. **Depends on:** T-304. **Used by:** T-402, T-403, T-404, T-405.

### What was built
`POST /runs/{id}/plan/sources` picks, for each contract entity, the table that serves it and records why, and maps each KPI's needed fields to columns. It writes `runs\<id>\SourceResolution.json` (versions in `resolutions\`) and returns it.

| File | Role |
|---|---|
| `config/glossary.yaml` | Terms and the words that name them (`product: [product, products, item, sku]`). Replaces the hardcoded `ALIASES`. |
| `app/discovery/glossary.py` | `load_glossary`, `Glossary.aliases_for`, `normalize`, `forms`. A bad file is `ConfigError` naming file and line. |
| `app/discovery/source_resolver.py` | Model prompt and schema, `parse_suggestions`, `name_match`, `resolve` (pure, deterministic). |
| `app/contracts/source_resolution.py` | `SourceResolution`, `EntityResolution`, `SelectedSource`, `RejectedSource`, `KpiFields`, `FieldMapping`, `UnmappedNeed`. |
| `app/workflow/source_stage.py` | `resolve_sources`, later `load_saved_resolution`. |
| `app/workflow/inventory_review.py` | New `approved_exception_ids` (table to approval id). |
| `app/discovery/data_profiler.py`, `requirement_data_matcher.py` | Read the glossary instead of `ALIASES`. |
| `app/api/runs.py`, `deps.py` | Route and `get_source_llm`. |
| `app/manual_tests/t401_offline_checks.py` | Offline checks and the fakes the later tasks reuse (`FakeSourceLlm`, fixtures). |

### Rules
- Candidates per entity: glossary name matches plus the model's suggested tables. Anything not in the inventory is discarded and logged.
- Name match: 1.0 if a glossary word is the table's whole name (a schema-wide prefix such as `SalesLT_`, and one leading qualifier such as `dim_`, are ignored); 0.7 if it is a run of words in the name; 0 for a model-only suggestion.
- Score `0.4*name_match + 0.3*column_coverage + 0.2*conformed + 0.1*relationship_confidence`, rounded to 2 decimals. Ties: conformed first, then table name.
- A non-conformed table is eligible only with an approved exception (its approval id is `exception_id`). Otherwise it is in `rejected` with `requires_exception: true`; if nothing is eligible `selected` is `null` with a `reason`.
- `kpi_fields` maps each KPI need the model lists to one column (selected tables first). Needs that can't be mapped are in `unmapped` with a reason (an addition to the task's shape; T-402 depends on it).
- The model's raw answer is saved in `source_suggestions.json` keyed by the request hash, so a second call gives a byte-identical file; the version grows only when content changes. A model failure is `502`/`504`, not a silent glossary-only result.

## T-402 KPI feasibility and Data Gap

**Spec:** business rule 8, §2.4, G1/G3 feasibility flags. **Depends on:** T-401. **Used by:** T-404, T-405.

### What was built
`POST /runs/{id}/plan/feasibility` decides, for each contract KPI, whether the mapped data can support it. Response `{"kpis": [Feasibility], "run": RunDetail}`; file `runs\<id>\Feasibility.json` (versions in `feasibility\`). It needs `SourceResolution.json` (`404` before `/plan/sources`).

| File | Role |
|---|---|
| `app/discovery/feasibility.py` | Prompt and strict schema, `available_columns`, `parse_needs`, `evaluate` (pure). |
| `app/contracts/feasibility_report.py` | `FeasibilityReport` (the file). `Feasibility` itself is in `business_contract.py` (T-201). |
| `app/workflow/feasibility_stage.py` | `check_feasibility`, `load_resolution`. |
| `app/workflow/llm_cache.py` | New: `request_key`, `saved_answer`, `save_answer` (shared with T-401). |
| `app/workflow/inventory_review.py` | New `raise_data_gaps` (several gaps, one transition). |
| `app/manual_tests/t402_offline_checks.py` | Checks plus `KPIS`, `SOURCE_ANSWER`, `FakeFeasibilityLlm`, `default_answer` reused later. |

### Rules
- The model lists each KPI's needs (formula intent, filters, time logic, exclusions) with a role (`measure`, `filter`, `time`, `dimension`) and the column that could supply each (`schema.table.column` or null). It sees KPI definitions and the names and types of the columns SourceResolution maps.
- Code decides: a need is met only if its column is mapped in `SourceResolution` and still in the inventory; a `time` need needs a date type. `SourceResolution.unmapped` counts as missing even if the model omits it. A KPI with `time_logic` but no time need, or with no needs, is a gap.
- One missing need makes the whole KPI `data_gap` (never partly feasible). Options on a gap: `drop_kpi`, `provide_source`, `data_engineering_task`.
- Any gap: one data gap per KPI in `data_gaps.jsonl`, run to `NEEDS_INPUT` (`resume_state: DATA_PROFILED`). A run in `NEEDS_INPUT` can't be checked again; resume it with `python -m app.cli runs transition RUN_ID DATA_PROFILED`.
- Unusable model output: one retry with the problem named, then `502 LLM_INVALID_OUTPUT`, nothing saved. Artifact status `data_gap` or `draft`.

### Steps to test

Expected: all `PASS`, last line `All checks passed.` Covers feasible and gap KPIs, the override by editing the resolution, a model claiming a missing column, one missing exclusion, time logic with and without a date column, unmapped needs, all KPIs gaps, `NEEDS_INPUT` and the gap list, no DAX or proxy in the run folder, the retry and the 502, and the 404/409 cases.

**Manual** (after the setup; run A has Net Revenue; run B has Net Revenue plus `Customer Retention Rate by quarter`, formula intent "customers active in two consecutive quarters over those active in the first", time logic "by quarter"; both `DATA_PROFILED`, and `POST /runs/{id}/plan/sources` done).

Expected: 200; `Customer Retention Rate` is `data_gap` with `missing` entries (for example "customer activity per period" and a quarter/date need, each with a reason) and `options: ["drop_kpi", "provide_source", "data_engineering_task"]`; `run.state` is `NEEDS_INPUT` with `resume_state: DATA_PROFILED`; `run.data_gaps` has an entry for the KPI. ## T-403 Bridge-table detection and proposal

**Spec:** FR-008, §15 (Bridge-Table Design), business rule 4. **Depends on:** T-401. **Used by:** T-404 (T-506 later generates bridges).

### What was built
`POST /runs/{id}/plan/bridges` finds many-to-many needs between the contract's resolved entities and proposes a bridge only when a mapping table or an approved derivation rule exists. It never guesses a mapping. Response `[BridgeProposal]`; file `runs\<id>\BridgeProposals.json` (versions in `bridges\`). It needs `SourceResolution.json` (`404`), a scope with a SQL endpoint and stored relationship evidence (`400 BAD_REQUEST`: run `/relationships/analyze` first).

| File | Role |
|---|---|
| `app/discovery/bridge_detection.py` | `find_mapping_tables`, `measure_mapping` (aggregate-only SQL), `detect`. |
| `app/discovery/derivation_rules.py`, `config/derivation_rules.yaml` | Approved rules: `id`, two `entities`, `description`, `approved_by`, optional `deduplicate: true`. Shipped empty with an example in comments. |
| `app/contracts/bridge_proposal.py` | `BridgeProposal` (with `deduplication_rule`), `BridgeProposals`. |
| `app/workflow/bridge_stage.py` | `propose_bridges`, `decide_bridge`, `MappingRulesRequired`. |
| `app/workflow/approval.py` | `perform` routes `BridgeProposal:<id>`; `AlreadyApproved` takes a message. |
| `app/api/runs.py`, `errors.py` | Route and the `409 MAPPING_RULES_REQUIRED` handler. |
| `config/conformed_sources.yaml` | Added `nexora_test.dim_promotion`, `bridge_product_promotion`, `dim_campaign`. |
| `app/discovery/source_resolver.py` | The name-matching fix (see Gotchas). |
| `app/manual_tests/t403_offline_checks.py` | Checks plus `BridgeSql`, a fake SQL endpoint reused by T-404 and T-405. |

### Rules
- A *mapping table* is a table no entity selected, whose every column joins (medium or high confidence) into entity tables, and that joins into at least two of them.
- A bridge is needed for such a pair, for a direct `many_to_many` between two selected tables, and for an *isolated* entity (its table joins to nothing; one `needs_rules` proposal lists the other entities too, for example `["Product", "Campaign"]`). A many-to-many between tables no entity uses is ignored and logged.
- Per pair: the mapping table with the highest summed coverage becomes `existing_table` (evidence `duplicate_pairs`, `coverage_a_pct`, `coverage_b_pct`, the aggregate `queries`; other candidates and duplicates in `issues`); else an approved rule becomes `derivation_rule`; else `needs_rules` with no table, and the run goes to `NEEDS_INPUT` with a data gap asking for the mapping rules.
- Approvals: `POST /runs/{id}/approvals` with `artifact: "BridgeProposal:<id>"`, `ACCEPT` or `REJECT`, `expected_hash` = the `BridgeProposals` artifact hash. ## T-404 ExecutionPlan and ModelSpec generation

**Spec:** FR-010, §8.4, §10, §2.3 (Direct Lake / Import). **Depends on:** T-402, T-403. **Used by:** T-405 and every later model, report and deployment task.

### What was built
`POST /runs/{id}/plan` builds `runs\<id>\ModelSpec.yaml` and `ExecutionPlan.yaml` deterministically (no model call) from the contract, the inventory with its relationship evidence, `SourceResolution`, `Feasibility` and, if present, `BridgeProposals`. It validates both and returns `{"execution_plan", "model_spec", "validation"}`. `GET /runs/{id}/plan` returns the saved files validated again (a hand edit shows up), in any state. It needs `SourceResolution.json` and `Feasibility.json` (`404`) and gives `409 NO_FEASIBLE_KPIS` if every KPI is a data gap. Artifacts `ModelSpec` and `ExecutionPlan` are `draft`; the plan's `based_on` is the model's hash; versions are in `plans\`.

| File | Role |
|---|---|
| `app/contracts/model_plan.py` | `ModelSpec`, `ModelTable`, `ModelColumn`, `Relationship` (with `override_rationale`), `Measure`, `RlsRole`, `ExecutionPlan`, `PlanSource`, `DataEngineeringAction`, and `save_yaml`/`load_yaml`/`to_data`. `extra="forbid"`; fixed key order, UTF-8, LF. |
| `app/discovery/model_planner.py` | `build_plan(PlanInputs)`, `NoFeasibleKpis`. |
| `app/discovery/plan_validation.py` | `validate_plan`: PLAN.1 to PLAN.10. |
| `app/workflow/plan_stage.py` | `generate_plan`, `read_plan`. |
| `app/cli.py` | `plan validate`. |
| `app/api/runs.py`, `schemas.py`, `errors.py` | Routes, `PlanResponse`, `409 NO_FEASIBLE_KPIS`. |
| `app/manual_tests/t404_offline_checks.py` | Checks plus `DETAIL_TO_HEADER`, `HEADER_TO_DATE`, `DATE_TABLE`. |

### How the plan is built
- **Tables:** facts (tables of the feasible KPIs' `measure` fields; grain from the KPI), entity tables, other tables the KPIs need, existing bridge tables, the date table. Table names are the entity name where an entity selected the table (`Sales`, `Product`), else the table name.
- **Relationships:** only stored evidence of medium or high confidence, `many_to_one` or `one_to_one`, between tables in the model; `evidence_ref` is the evidence id. Names are `<from>_<to>`.
- **Measures:** feasible KPIs only; `dax: null`; `description: "Approved: <formula intent>"`; format from the currency (`$#,0` for USD).
- **Columns:** only types the model can hold; foreign keys and measure source columns are hidden.
- **RLS:** one `RLS<n>` role per `contract.security` entry, no filter; none means `roles: []`, never inferred. **Storage mode:** `DirectLake`.
- **Date table:** added when a KPI has time logic or a time field: a conformed table named for dates with a date column, with a Calendar hierarchy (Year, Quarter, Month). If there is none: a blocking `create_date_table` action in `data_engineering_actions` and no calculated table. A bridge proposal without a physical table becomes a `create_bridge_table` action.
- **ExecutionPlan:** sources with `conformed`/`exception_id`; stages `semantic_model` (G4), `report` (G5), `deployment` (G6); `target` = `FABRIC_SANDBOX_WORKSPACE_ID` or else the run's workspace; `approvals_required` G3 `[bi_engineer]` and G4 `[bi_engineer, business_owner]`; `bridges`; `data_engineering_actions`; `feasibility_ref`.
- **Validation PLAN.1-10:** references exist (failures name the path), relationship evidence or override, unique names and no double relationships, no calculated tables under Direct Lake, sources conformed, measures feasible, no DAX yet (warning), RLS only from the contract, a date table or action, connectivity (warning).
- A re-run with nothing changed keeps both versions. An unreadable hand-edited file is regenerated as the next version.

## Gotchas

- **Name matching (T-401).** A table is "named" by a word only if that is its whole name or the name after one leading qualifier. Treating any suffix as the name made `bridge_product_promotion` win as the *Promotion* table and hid the bridge (found while building T-403). If you change `name_match`, run `t401` and `t403`.
- **The date join needs evidence.** `Header.OrderDate -> dim_date.Date` isn't a naming pattern, so it is in the plan only if the model proposed it or you sent it as a user candidate to `/relationships/analyze` (body in the T-404 steps). Without it G3.3 and G3.6 fail and say so.
- **Relationship names** are `<from>_<to>` in model table names. The task text's "Sales_Date" is `SalesLT_SalesOrderHeader_Date` here; read the real names on the screen.
- **T-102's offline check** forbids `PUT`/`PATCH`/`DELETE` endpoints that could change run state, with named exceptions (`/scope`, `/contract/kpis/`, `/plan`). A new edit endpoint needs an exception, with the reason.
- **Line endings.** Repo files are CRLF and tools often write LF. After a scripted edit check `git diff --stat`; if a whole file shows as changed, normalize it back (bytes: `\r\n` to `\n`, then `\n` to `\r\n`). It happened to `.claude/MANUAL_TESTING.md`.
- **Windows tooling.** Long here-documents with quotes failed in the Bash tool ("unexpected EOF"); the editor tool or a small Python script worked. A `cd` can leave the shell inside `rayfin-ui`, so use absolute paths. `python -m app.cli plan validate` imports the app's config, so it needs a `.env`.
- **A flaky check.** `t403` ("a derivation_rule proposal can be approved") failed once in a loop and then passed on many later runs; the cause is unknown. Re-run once, then investigate.
- **Hand edits after approval.** T-502 compares `ModelSpec.yaml` with the approved hash (`409 STALE_VERSION`), so don't edit the plan files by hand after Accept; return the run first.
