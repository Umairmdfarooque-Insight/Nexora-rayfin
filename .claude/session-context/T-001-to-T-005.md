## 3. T-001 — Dependencies and configuration loading

**What was built**
- `app/runtime.py` (new): `RUNTIME: Literal["local", "fabric_job", "fabric_udf"]`, detected once by trying `import fabric.functions` (UDF host) then `import notebookutils` (job), else `local`. No other module probes the environment.
- `app/config.py` (rewritten): resolution order is process env → Variable library `nexora_settings` (Fabric only, via `notebookutils.variableLibrary.getLibrary("nexora_settings")`, fetched once and cached module-level) → `.env` (local only). `get_required_setting`/`get_optional_setting` keep their names and shapes. Added `setting_source(name)` (reports `"environment"`/`"nexora_settings"`/`".env"`/`None`, never the value — needed `_environ_before_dotenv`, a snapshot of `os.environ` taken *before* `load_dotenv` runs, because `load_dotenv` merges `.env` into `os.environ`, which would otherwise make every `.env` value look like it came from "environment") and `required_setting_names()` (the three `AZURE_OPENAI_*` names).
- **Design decision, not fully spelled out in the task text:** `AZURE_OPENAI_ENDPOINT`/`DEPLOYMENT`/`API_KEY` are **never** eagerly required inside `app.config` itself, in *any* runtime (not just `fabric_udf`). `app/llm/client.py` requires them again at its own import. The task's FR only explicitly exempts `fabric_udf`; reading it as exempting every runtime equally turned out to be the design that actually satisfies everything at once: T-001's own AC-3/AC-4 test via `import app.llm.client`, not `import app.config`, so this is unobservable from those two ACs either way — but T-003's `settings` check needs `app.config` to import successfully even when a required setting is missing, so it can report that setting's check as a `fail` instead of crashing the whole smoke run (and, in a job, instead of crashing `nexora_stage_runner` before any other check gets to run). Eager-requiring in `app.config` for `local`/`fabric_job` would have broken that. If a later task wants `app.config` itself to fail fast for these three outside a UDF, that's a real behavior change against what's built now, not just a wording fix — re-check both T-001's and T-003's acceptance criteria before making it.
- Added proper `app.config` constants for settings that were previously read ad hoc with `get_optional_setting` at each call site: `RUN_STORE`, `FABRIC_CONTROL_DB_SERVER`, `FABRIC_CONTROL_DB_NAME`. **This fixed a real bug**: `app/tools/smoke.py`'s shared `_require_settings` helper does `getattr(config, name)`, and calling it with `"FABRIC_CONTROL_DB_SERVER"` crashed with `AttributeError` before this was added — caught by actually running the `control` check offline with `RUN_STORE=fabric_sql`, not by reading the code.
- New optional settings: `NEXORA_HOME_WORKSPACE_ID`, `NEXORA_CONTROL_LAKEHOUSE_ID`, `NEXORA_STAGE_RUNNER_ID` (blank until T-005's `deploy_home` writes them).
- `pyproject.toml` (new): `name = "nexora"`, static placeholder `version = "0.0.0"`, `dynamic = ["dependencies"]` reading straight from `requirements.txt` (`[tool.setuptools.dynamic]`) so there's one source of truth for the dependency list, not two files to keep in sync. `T-005's app/tools/package.py` rewrites the version line in place before building and restores it after.
- `requirements.txt`: added `mssql-python` (the T-002 SQL driver fallback).
- `.gitignore`: added `/dist/`, `/build/`, `*.egg-info/`. `.env.example`: added the three `NEXORA_*` names, blank.

**Verified offline (actually run, not just read):** AC-1 (`pip wheel . --no-deps -w dist` → `nexora-0.0.0-py3-none-any.whl`), AC-2 (`Nexora local`), AC-3 (commented out `AZURE_OPENAI_API_KEY`, `import app.llm.client` → the exact `ValueError` text), AC-4 (whitespace `AZURE_OPENAI_DEPLOYMENT`, same), AC-5 (`cd C:\`, `sys.path.insert`, still finds `.env`), AC-7 (`import app.test_llm, app.test_fabric_sql, app.test_metadata_inventory`, no error). AC-6 (Variable library in a real job) needs T-005's home workspace and a live sign-in — left for the user.

## 4. T-002 — One token provider

**What was built**
- `app/auth.py` (rewritten): single entry point `get_token(scope)` branches on `RUNTIME`.
  - `local`: unchanged — the existing shared `InteractiveBrowserCredential` with its on-disk cache (the old `get_token` body, renamed `_get_token_local`).
  - `fabric_job`: `notebookutils.credentials.getToken(audience)`, with a scope→audience map (`_JOB_AUDIENCE_BY_SCOPE`) and a 5-minutes-before-expiry cache keyed by scope (`_job_token_cache`, expiry read by decoding the JWT's `exp` claim without verifying the signature — Fabric issued it, we just need to know when to refresh). A failure raises `ConsentRequired(RuntimeError)` naming the scope, never the token.
  - `fabric_udf`: always raises `RuntimeError("Source access is not allowed in a User Data Function; run this operation as a job")` — the exact string the task's API contract specifies.
  - `get_credential()` stays local-only (raises `RuntimeError` in Fabric). New `current_identity() -> {oid, upn, name} | None`: best-effort from `notebookutils.runtime.context`'s `userId`/`userName` (there's no documented separate UPN field, so `name` and `upn` both come from `userName` until a live job confirms otherwise — flagged in `fabric-hosting.md`).
- **No connector needed a signature change.** The research fork confirmed every connector (`FabricLakehouseConnector`, `FabricSQLConnector`, `FabricApiClient`, `PowerBiClient`, `FabricItemsClient`) already took an optional `token_provider` defaulting to `get_token(SCOPE)`, so rewriting `get_token`'s internals was sufficient — exactly what the task's own constraint ("connectors' public methods keep their signatures") expects.
- `app/connectors/fabric_sql_connector.py`: `_select_driver()` tries `pyodbc` with `"ODBC Driver 18 for SQL Server"` registered, falls back to `mssql_python` (a pure-Python driver, no native ODBC install needed) if that's unavailable, raises clearly if neither is. Both `import pyodbc` and `import mssql_python` moved inside functions (lazy), so the module itself imports fine with only one of the two installed — important for a notebook runtime that might only have one.
- **Deliberately left `app/api/deps.py` and `app/api/obo.py` untouched.** The task's FR-3 reads as forward-looking documentation of what changes once T-102 removes `app/api/`, not an action item for T-002 itself: T-002's own "API contracts" section only defines `app.auth` members, and `app/api/` (the local-dev FastAPI fallback) still needs its OBO flow to keep working until T-102 actually retires it. If a review disagrees with this reading, it's a one-paragraph fix, not a redesign.
- Recorded the scope→audience mapping and its sourcing (docs list `storage`/`pbi`/`keyvault`/`kusto` as the only short keys; `pbi` covers both Power BI and Fabric REST; there's no short key for the SQL endpoint, so `SQL_SCOPE`'s raw `.../.default` string is passed through directly, matching community-reported usage) in `fabric-hosting.md`, not just in a code comment.

**Verified offline:** `get_credential() is get_credential()` → `True` (unchanged local singleton behavior). Everything else (job behavior, UDF refusal from a real UDF host, which driver Fabric's notebook runtime actually has) needs a live sign-in and T-005's home workspace — left for the user, with exact commands in `MANUAL_TESTING.md`.

## 6. T-005 — Nexora home workspace and Fabric packaging

**What was built**
- `app/tools/package.py` (new): `compute_version()` → `0.<git rev-list --count HEAD>.0+<short sha>`, or `0.0.0+nogit` (this repo has no `.git`, so this is the path actually exercised). `build_wheel(version)` temporarily rewrites `pyproject.toml`'s `version =` line, runs `pip wheel . --no-deps -w dist` with `SOURCE_DATE_EPOCH` pinned, then restores the file (always, via `finally`, even on failure). `copy_config()`/`write_manifest()` produce `build/config/*.yaml` and `build/manifest.json` (`wheel`, `wheel_hash`, per-config-file hashes).
  - **Real bug caught by actually running it twice, not by reading the code:** the first version fell back to `SOURCE_DATE_EPOCH="0"` (1970-01-01) outside git, and Python's `zipfile` refuses `ValueError: ZIP does not support timestamps before 1980` — `pip wheel`'s own dependency-install step crashed on `pip`'s own console-script generation before even reaching this project's code. Fixed with a named constant `_ZIP_EPOCH_FLOOR = "315532800"` (1980-01-01T00:00:00Z) as the no-git fallback instead of `"0"`.
  - Verified deterministic: built twice from a clean `dist`/`build`, identical `wheel_hash` both times.
- `app/deploy/fabric_items.py` (existing T-501 client, extended): `create_workspace`, `get_workspace` (workspace-level, not subject to the existing sandbox-only `_check_target` guard — there's no target to check yet when creating one), `upsert_item(workspace_id, display_name, item_type, definition=None, dry_run=False)` (generic create/update/unchanged for item types without one of the existing dedicated `_upsert` paths — Lakehouse, SQLDatabase, Eventhouse, Environment, UserDataFunctions, VariableLibrary — comparing definition-part hashes via the generic `getDefinition`/`items` collection to decide "updated" vs "unchanged", with a `dry_run` mode that only reads), `upload_environment_library`/`publish_environment` (the Environment-specific staging-library upload and publish flow, distinct from the generic item definition flow).
  - **Verified with a fake HTTP transport** (no network): create → unchanged on an identical rerun → updated when the definition's content actually changes → a bare (no-definition) item's create → unchanged rerun → a same-name-different-type call raises `NameConflict`. All five paths behaved correctly on the first try, which is exactly why a test like this is worth writing before trusting new client logic you can't run against the real API.
- `app/tools/deploy_home.py` (new): `--env dev|test|prod [--create NAME] [--dry-run]`. `resolve_target_workspace` (verified with mocks: reuses an existing same-named workspace on `--create` instead of creating a duplicate; the `Nexora-` prefix and the "no `--create` and no `NEXORA_HOME_WORKSPACE_ID`" cases both raise `BadArguments` **before any Fabric call**, giving exit `2` with zero network round-trips — verified by literally running these three argument combinations offline). `deploy()` creates/updates all seven items, resolves ids, folds them into `nexora_settings`' value set for `--env` (built last, after the other six ids are known), uploads+publishes the wheel only when its hash differs from the previous `build/manifest.json` (so a no-op rerun doesn't needlessly republish the Environment), and publishes `config/*.yaml` to the control Lakehouse.
- `fabric/` (new folder, committed Git-format item definitions): `nexora_stage_runner.Notebook/` (a real, valid `.ipynb` wiring `operation = "smoke"` to `app.tools.smoke.run_job`, plus a placeholder `raise NotImplementedError` for everything else until T-102), `nexora_settings.VariableLibrary/` (`variables.json` + `valueSets/{dev,test,prod}.json`), `nexora_api/` (just `.platform` + a `README.md` explaining the gap below — no function code, since T-102 owns that). ## 7. Gotchas learned this session

- **This repo has no `.git`.** Don't assume one exists; check before trying branch/commit skill steps. Ask the user how they want version control handled, same as this session did — don't silently `git init` or silently skip it.
- **`app.config`'s eager-vs-lazy required-setting design has a non-obvious dependency on T-003's smoke check.** See the T-001 section above before "fixing" it to eagerly require the three `AZURE_OPENAI_*` settings again.
- **`SOURCE_DATE_EPOCH` must be ≥ `315532800` (1980-01-01), not `0`.** `zipfile` (and therefore any wheel build) raises on anything earlier. Easy to miss because the error surfaces deep inside `pip`'s own build-isolation step, not in this project's code.
- **`smoke.py`'s `_require_settings(*names)` does `getattr(config, name)`.** Any setting it's asked to check must be a real `app.config` module-level constant, not just something resolvable via `get_optional_setting` at a call site — this is what the `FABRIC_CONTROL_DB_SERVER`/`NAME` bug was.
- **Write a fake-transport test for new `FabricItemsClient` logic before trusting it**, even though (especially though) there's no live tenant to check it against here — it's the only way to catch a logic bug in code you otherwise can't run.
- **The `.platform` file inside a Fabric Git-format item folder is a real file named exactly `.platform`** (dot-prefixed) at the item folder's root, not a special wrapper; `_folder_parts()` includes it as an ordinary file via `Path.rglob("*")` (which doesn't skip dotfiles), with its `path` in the definition parts list being the literal relative path `.platform`.
- **Run Python as `.venv\Scripts\python.exe -m app.xxx` from the project root**, same note every other session's file makes. A `py -3.12 -m venv .venv` is needed since the system default `python` here was 3.14 (the repo pins 3.12).
