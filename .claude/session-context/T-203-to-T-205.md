## 2. The flow

```
CREATED                       POST /runs/{id}/compile              T-202  draft contract, rule questions
  |  blocking question open
NEEDS_CLARIFICATION           POST /runs/{id}/questions/{qid}/answer     T-203  answer -> locked fact -> recompile
  |  no blocking question     POST /runs/{id}/questions/{qid}/dismiss    T-203  non-blocking only, with a reason
CREATED                       PUT  /runs/{id}/contract/kpis/{name}       T-203  owner edits a KPI (draft only)
  |                           POST /runs/{id}/gates/G1/check             T-204  gates/G1-<ts>.json
  |                           POST /runs/{id}/approvals                  T-204  ACCEPT | EDIT | REJECT | EXPLAIN | REGENERATE
  |  ACCEPT with G1 passing   GET  /runs/{id}/approvals                  T-204  approvals.jsonl as a list
REQUIREMENT_APPROVED          GET  /me                                   T-205  roles of the caller
                              UI: /runs/[id] (clarification panel), /runs/[id]/contract (review)   T-205
  REJECT -> back to NEEDS_CLARIFICATION with a blocking reviewer question (REV-<n>)
```

Files in `runs/<id>/`: `BusinessContract.yaml` (current), `contracts/BusinessContract.v<n>.yaml` (every version, never modified), `approvals.jsonl` (append-only), `gates/G1-<timestamp>.json`, `logs/compile-<ts>.json` (compile failures and locked-fact warnings). The artifact `BusinessContract` in the manifest holds the current `version`, `hash` and `status` (`draft` or `approved`); **its hash is what the API and UI send as `expected_hash`**.

## 3. Working rules that applied to every task (keep following them)

- **The model proposes, deterministic code decides.** In this session the model is used only by the compile graph (T-202's graph, re-run by answers and by Regenerate). Everything else is code: locked-fact enforcement, G1, Explain, KPI edits, the role check, the state moves.
- **No silent KPI assumptions.** A user's answer to a critical-term question is written verbatim as the KPI's `formula_intent`; nothing is inferred.
- **The graph never changes run state or writes the manifest.** `compile_run` (the service) writes the contract files, registers the artifact and makes the transition; the graph only returns a contract and warnings.
- **Only the store writes manifests;** the services write the contract, gate and approval files.
- **Every approval action is attributable:** a record in `approvals.jsonl` with the user's UPN, a timestamp and the artifact hash. A refused action (403, 409, 422) writes nothing and changes nothing.
- **Config files are read on every call** (`config/roles.yaml`), so an edit applies without restarting; a bad file is `500 CONFIG_ERROR` naming the file, and the API also checks `roles.yaml` at startup.
- **Handlers hold no business logic:** `api/runs.py` calls the services in `app/workflow/`.
- **The UI holds no business logic:** whether Accept is possible is decided by the API (G1). The UI only reads the result and disables the button (`src/lib/review.ts`).
- **Never read or print `.env`.** Never commit a real UPN in `config/roles.yaml` unless you mean to publish it (the repo is public).
- **Task workflow:** `/implement-task T-xxx` creates the branch from `main`, implements, runs the offline checks, updates `.claude/MANUAL_TESTING.md` and `.claude/CLAUDE.md` and stops at `Awaiting manual test`; `/commit-push` commits and pushes; `/cleanup-branch` deletes a merged branch.

## 5. T-203 Clarification loop

**Spec:** FR-002, FR-003, §8.2 (locked facts). **Depends on:** T-202.

### What was built
Three actions on a draft contract, all in `app/workflow/clarification.py`, exposed by three routes:

| Route | Request | Response |
|---|---|---|
| `POST /runs/{id}/questions/{qid}/answer` | `{"answer": str}` (1-2000 chars, trimmed) | `{"run", "contract"}` |
| `POST /runs/{id}/questions/{qid}/dismiss` | `{"reason": str}` (1-2000 chars) | `{"run", "contract"}` |
| `PUT /runs/{id}/contract/kpis/{kpi_name}` | partial KPI plus `expected_hash` | `{"contract"}` |

An **answer** marks the question `answered` with the text, stores a **locked fact** `LF-<qid>` (`source_question_id` = the question) and recompiles, so the state moves `NEEDS_CLARIFICATION` to `CREATED` when no blocking question is left. A **dismissal** closes a non-blocking question (`status: dismissed`, `dismiss_reason`). A **KPI edit** changes only the fields sent.

| File | Role |
|---|---|
| `app/workflow/clarification.py` | `answer_question`, `dismiss_question`, `edit_kpi`; exceptions `NotFound`, `ContractLocked`, `StaleVersion`, `QuestionConflict`. (`apply_kpi_edits` was extracted from `edit_kpi` in T-204, see section 6.) |
| `app/workflow/compile_stage.py` | `compile_run` takes `previous=` (the contract to recompile from) and `action=` (the wording of a `WrongState` message); `save_contract_version` is the shared "write the next version file and the current file and register the artifact" helper; `_write_compile_log` writes failure logs and warnings |
| `app/compiler/critical_terms.py` | `apply_locked_facts(contract, previous, config, warnings)` now also carries **dismissed** questions and re-applies a term's locked fact; helpers `term_for_fact`, `matching_kpi_index`, `_enforce_term_facts` |
| `app/compiler/requirement_compiler.py`, `app/graphs/compile.py` | `compile_requirement(..., warnings=)` returns warnings out of the graph state; system prompt rule 8 says locked facts and answered questions must never be contradicted; the LLM schema excludes the new `dismiss_reason` field |
| `app/contracts/business_contract.py` | `QuestionStatus.DISMISSED`, `OpenQuestion.dismiss_reason`, rule "a blocking question can't be dismissed"; `schemas/business_contract.schema.json` regenerated |
| `app/api/runs.py`, `schemas.py`, `errors.py` | the routes, `AnswerRequest`, `DismissRequest`, `QuestionResponse`, `KpiEditRequest`, `KpiEditResponse`, the error mappings |

### Rules
- Allowed only while the contract is `draft` and the run is in `CREATED` or `NEEDS_CLARIFICATION`. Check order (shared by the three actions, `_editable`): no contract file gives `404 NOT_FOUND`; an `approved` contract gives `409 CONTRACT_LOCKED`; a wrong run state gives `409 WRONG_STATE`. Then, for a KPI edit, a stale hash gives `409 STALE_VERSION` (details `expected_hash` and `current_hash`) and an unknown KPI `404 NOT_FOUND`; for the other two an unknown question is `404 NOT_FOUND`. A run id that doesn't exist is `404 RUN_NOT_FOUND`.
- `qid` and `kpi_name` come from the URL. `kpi_name` is matched ignoring case. An empty answer or reason is `422 VALIDATION_ERROR` (Pydantic).
- **An answer is one atomic step.** `answer_question` builds the contract with the answer already applied and passes it to `compile_run(previous=…)`. If the recompile fails (`502 LLM_INVALID_OUTPUT`, `504`, ...) nothing is saved and the user sends the answer again.
- **Re-answering** an answered question (or answering a dismissed one) is allowed in draft: the locked fact `LF-<qid>` is replaced. The old answer stays only in the earlier `contracts/BusinessContract.v<n>.yaml` files.
- **Locked facts win over the model.** After every recompile `apply_locked_facts` carries the previous answered and dismissed questions and the locked facts unchanged. A fact whose `source_question_id` is a `RULE-<TERM>` question is the definition of that term: the **first KPI whose name mentions the term or an alias** gets `formula_intent` = the fact's text. If the model had written a different non-empty `formula_intent`, the override is a warning ("LLM output contradicts locked fact …") written to `logs/compile-<ts>.json`; nothing is logged when the model agreed or wrote nothing.
- **A KPI edit that sets `formula_intent` on such a KPI also updates the locked fact's text and time**, so a later recompile keeps the owner's wording instead of resetting it (FR-003). Editable KPI fields: `formula_intent`, `grain`, `filters`, `time_logic`, `exclusions`, `currency`, `expected_examples`, `rationale` (not `name` or `status`; the PUT body is `extra="forbid"`, so those are `422`).
- **Dismissing:** only an `open`, non-blocking question. A blocking one is `409 QUESTION_CONFLICT` ("blocking questions must be answered"); an already answered or dismissed one is `409 QUESTION_CONFLICT` too. A dismissal and a KPI edit write a **new contract version** without calling the model and leave the run state alone.
- Rule question ids are `RULE-<TERM>` (for example `RULE-REVENUE`), not `Q1`: the task text says `Q1` in its acceptance steps, but the question about how Revenue is defined is `RULE-REVENUE`. Model questions are `Q1`, `Q2`, ...
- Each action bumps the version: `max(existing version files) + 1`.

### Steps to test

### Rules
- **Roles:** `config/roles.yaml` maps `business_owner`, `bi_engineer`, `security_reviewer`, `project_reviewer`, `data_engineer`, `release_approver` to UPN lists; an unknown role name is a config error. Matching ignores case. One person may hold several roles. The file is **read on every request**, so a change applies at once. A missing or invalid file is `500 CONFIG_ERROR` naming `roles.yaml` (and the API refuses to start). **Only `business_owner` may Accept or Reject the contract**; Edit, Explain and Regenerate need only a signed-in user.
- **Order of checks in `perform`** (the first failure wins, nothing is written): artifact other than `BusinessContract` is `422` (`UnknownArtifact`); no contract file is `404 NOT_FOUND`; Accept or Reject without the role is `403 FORBIDDEN`; for every action except Explain: an `approved` contract is `409 ALREADY_APPROVED` (Accept) or `409 CONTRACT_LOCKED` (anything else), a run state other than `CREATED`/`NEEDS_CLARIFICATION` is `409 WRONG_STATE`; then `expected_hash` must equal the artifact's hash (`409 STALE_VERSION`, Explain included); then the action runs.
- **Gate G1** (`run_g1`, deterministic): **G1.1** the contract passes the schema and rules (re-validated from the saved content); **G1.2** no blocking question open; **G1.3** every KPI has `formula_intent`, `grain` and `currency` (**and there is at least one KPI**: an addition, because "every KPI" is vacuously true for none); **G1.4** no KPI with `status: data_gap`; **G1.5** feasibility: with no feasibility entries it is a `warning` "not yet assessed" (T-402 fills them), with entries a KPI that has none fails. `passed` = no check is `fail`. A warning never blocks.
- **ACCEPT:** runs G1 on the current contract and saves the gate file (also when it fails). A failure is `409 GATE_FAILED` (`details.failed_checks` lists ids, `details.gate_result` has all checks) and nothing is locked or recorded. Only then is the run state checked (`CREATED` required). On success the contract is written as the **next version with `status: approved`** (the artifact becomes `approved`, its hash is the approved file's hash) and the run moves `CREATED → REQUIREMENT_APPROVED` with the user's UPN as actor.
- **REJECT** (comment required, `422` otherwise, blank counts as empty): appends a **blocking** question `REV-<n>` (`n` = highest existing `REV-` number + 1) with `text` = the comment, `source: reviewer`, `reason: "Rejected by <upn>"`, writes a new version and moves `CREATED → NEEDS_CLARIFICATION` (a run already in that state just stays). The question is answered like any other (`/answer`) and survives recompiles until then.
- **EDIT:** `edits = {"kpis": {"<kpi name>": {fields}}}`, same fields and locked-fact sync as the PUT route, but **recorded** in the approvals log (the UI uses this one). An unknown KPI is `404`, an unknown field `422`.
- **EXPLAIN:** returns `{"kpis": [{name, status, rationale}], "questions": [{id, text, blocking, status, source, rationale}]}`, built by code from the contract ("X is defined as: ... Grain ... Currency ...", or "has no definition yet", plus the contract's `rationale`; for a question "Asked because: <reason>"). No model call. Allowed in every state, also on an approved contract. Records an `EXPLAIN` entry.
- **REGENERATE:** `compile_run` with the comment as `guidance`; locked facts and answers are kept by the usual carry-over. The record holds the version and hash **before** the regeneration (the one the reviewer looked at).
- **Approval record** (`ApprovalRecord`, one JSON line in `approvals.jsonl`): `approval_id`, `run_id`, `artifact`, `artifact_version`, `artifact_hash`, `target` (null), `action`, `role` (`business_owner` first, else the first role the user holds, else null), `user {oid, upn}`, `at`, `comment`, `gate_result_ref` (set on Accept). Version and hash are those of the version the action acted on, **except Accept and Edit, which record the version they produced**. A refused action writes no record. The file is only ever appended to.
- G1.5 and the role list are the two places a later task fills in (T-402 for feasibility, the other roles for later gates).

## 8. Gotchas learned in this session

- **The Revenue question is `RULE-REVENUE`, not `Q1`.** Task text and acceptance steps written before T-202 say `Q1`; use the real id. Questions the model adds are `Q1`, `Q2`, ... and a rejection's are `REV-1`, ...
- **Answering recompiles with the real model**, so each answer in a live test takes seconds and can fail with `502`/`504`; the answer is then not saved (by design).
- **The fake model in the offline checks renames the KPI.** `t203`'s `FakeLlm` picks the KPI name `Net Revenue` when the *prompt* contains it, and the prompt contains the previous contract including the user's answer, so after an answer the KPI is `Net Revenue`, not `Revenue`. Look the name up from the contract instead of hardcoding it (the checks do).
- **A test that moves a run to `REQUIREMENT_APPROVED` through the store must go through `CREATED` first:** `NEEDS_CLARIFICATION → REQUIREMENT_APPROVED` is illegal (the state table allows `NEEDS_CLARIFICATION → CREATED` only).
- **The G1 gate is checked before the `CREATED` state check on Accept**, so a run that still has a blocking question reports `GATE_FAILED` (with the reasons) rather than `WRONG_STATE`.
- **`config/roles.yaml` is committed and public.** The shipped file has `user@contoso.com` everywhere. When you test, put your own UPN in and restore it (`git checkout config/roles.yaml`) before `/commit-push`.
- **The artifact hash changes with every action** (edit, reject, accept, regenerate, answer, dismiss all write a new version). A hash read before an action is stale after it; the UI re-reads the run from each response.
- **Accepting writes a new version** (the approved copy), so the hash in the approval record is the approved file's hash, while the gate result's `artifact_hash` is the draft that was checked.
- **CRLF files:** many files are CRLF. A script that reads and writes a file in text mode silently changes line endings; read and write with `newline=""`, detect `\r\n`, and check `git diff` shows only your lines. Python string escapes in such scripts bite: a `\n` inside an edited Python/TS string literal became a real newline once (a syntax error) — check the result.
- **Windows and Git Bash:** `/tmp` in Git Bash is not the same path for `.venv\Scripts\python.exe`; use real Windows paths (or the session scratchpad) for helper scripts. Long multi-heredoc shell commands with apostrophes can fail to parse as one command; write helper scripts to files instead.
- **Windows file locks:** `app/manual_tests/t102_offline_checks.py` once raised `PermissionError` on `os.replace` in a temp folder (a scanner holding the file) and then did not on a rerun; if you see it, rerun before suspecting your change. Later work added `app/fsutil.py:replace_file` to retry such renames.
- **`app/manual_tests/t102_offline_checks.py` allows the KPI-edit `PUT`** in its "no endpoint changes state" check (the `/contract/kpis/` path); a new write endpoint needs the same treatment there.
- **`GET /me` is not in the task's API table;** it was added in T-205 because the UI needs the roles to hide actions.
- **Browser behaviour was not run by the session** (it needs an Entra sign-in and the real model); the UI's pure display rules have unit tests, the components themselves have none.
