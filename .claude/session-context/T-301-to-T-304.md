## 2. The pipeline

```
REQUIREMENT_APPROVED   (contract approved, scope bound with PUT /runs/{id}/scope)
  POST /runs/{id}/harvest                      T-301  -> MetadataInventory.json   (GET /runs/{id}/inventory returns it)
  POST /runs/{id}/profile                      T-302  -> profiles in tables[].profile
  POST /runs/{id}/relationships/analyze        T-303  -> relationship_evidence    (GET /runs/{id}/relationships returns it)
  POST /runs/{id}/gates/G2/check               T-304  -> gates/G2-<ts>.json
  POST /runs/{id}/exceptions                   T-304  an approved exception for a non-conformed candidate table
  POST /runs/{id}/approvals {"artifact": "MetadataInventory", "action": "ACCEPT", "expected_hash": ...}
                                               T-304  -> DATA_PROFILED
  POST /runs/{id}/data-gaps                    T-304  -> NEEDS_INPUT (the failure action)
  UI: /runs/[id]/inventory                     T-304  does all of the above from Rayfin
DATA_PROFILED
  POST /runs/{id}/harvest again                T-301  re-harvest: back to REQUIREMENT_APPROVED, new draft inventory, no profiles, no evidence
```

Everything lives in one artifact, `runs/<id>/MetadataInventory.json` (copies per harvest in `runs/<id>/inventories/MetadataInventory.v<n>.json`). Harvest creates a new **version**. Profiling, relationship analysis and (nothing else) rewrite the current file and its same-version copy in place and change only the artifact's **hash**, never its version (`harvest_stage.save_inventory`).

## 3. Working rules that applied to every task (keep following them)

- **The model proposes, deterministic code decides.** Only T-303 uses a model (it suggests candidate joins). A name the model returns is never trusted: the evidence step rejects any table or column outside the inventory.
- **Inventory metadata is the source of truth** for which tables and columns exist.
- **The model never sees data.** Its payload is the contract summary plus table and column names and types. Profiles store no row values: counts everywhere, and min and max only for date and numeric columns, never for strings.
- **Read-only SQL.** Only `SELECT`, identifiers always bracket-quoted from the inventory (`data_profiler.quote_identifier`, `]` escaped), aggregate-only evidence queries, 120 s statement timeout.
- **The user's identity.** OneLake and the SQL endpoint are called on behalf of the signed-in user (OBO): `api/deps.py:get_connector_factory` (storage scope) and `get_sql_connector_factory` (SQL scope). The API's app registration needs the Azure SQL Database `user_impersonation` permission with consent for the profiler, relationship analysis and G2 checks.
- **Stage services are plain functions** (no LangGraph graph): none of these stages has an LLM loop. Route handlers in `api/runs.py` only call them. A stage never changes run state, except Accept of the inventory (`DATA_PROFILED`), a re-harvest from `DATA_PROFILED` and a data gap (`NEEDS_INPUT`).
- **No hardcoded table names in code**; they live in `config/`.
- **Config files are read on every call**, so an edit applies without restarting the API; a bad file is `500 CONFIG_ERROR` naming the file. Added here: `config/relationship_thresholds.yaml` (T-303) and `config/conformed_sources.yaml` (T-304).
- **Percentages are 0-100** (`overlap_pct`, `orphan_rate`, `null_rate`, and the thresholds).
- **Task workflow:** `/implement-task T-xxx` creates the branch from `main`, implements, runs the offline checks, updates `.claude/MANUAL_TESTING.md` and `.claude/CLAUDE.md` and stops at `Awaiting manual test`; `/commit-push` commits and pushes; `/cleanup-branch` deletes a merged branch.

## 4. Setup shared by all manual steps

Do this once; the per-task steps refer to it as "the setup".

1. **Environment.** Windows, Python 3.12 virtualenv in `.venv` (`.venv\Scripts\activate`), a `.env` copied from `.env.example` with the model and Entra settings filled in (never print it). ODBC Driver 18 for SQL Server is needed for the SQL endpoint.
2. **Start the API:** `uvicorn app.api.main:app --reload --port 8000` (Swagger at <http://localhost:8000/docs>). **Start the UI** for T-304: `cd rayfin-ui; npm install; npm run dev`, sign in at <http://localhost:3000>.
3. **Get a token for Swagger:** sign in to the UI, press F12, *Network*, click any request to `localhost:8000`, copy the part of the `Authorization` header after `Bearer `; in Swagger click **Authorize** and paste it. It lasts about an hour; treat it like a password.
4. **Roles:** open `config\roles.yaml` and put **your own UPN** in the role the step needs (`business_owner` to approve the contract, `data_engineer` for exceptions and for Accept of the inventory). Restore it afterwards with `git checkout config/roles.yaml`.
5. **Fixtures:** the `nexora_test` schema (`dim_product_dupes` and others) comes from `fixtures/create_test_tables.ipynb` (see `fixtures/README.md`). `python -m app.test_metadata_inventory nexora_test` lists it.
6. **Get a run to `REQUIREMENT_APPROVED`:** in the UI open `/runs/new`, enter a prompt (for example `Show total sales by product and customer`), pick the workspace and Lakehouse and the schemas (`saleslt`, plus `nexora_test` where a step says so), create the run; on the run page **Compile**, answer the blocking questions, compile again until none is blocking; open `/runs/{id}/contract`, check G1 and **Accept** as `business_owner`.
7. **Clean up afterwards:** stop the API and UI, restore the config files you edited (`git checkout config/roles.yaml config/conformed_sources.yaml`), delete the test runs' folders under `runs\`.

The **offline checks** need none of this (no sign-in, no network): `python -m app.manual_tests.tNNN_offline_checks`. They build on each other: `t303` imports the fixtures of `t302` and extends them, and `t304` imports `t303`, so after changing a fixture re-run all of `t301` to `t304`.

## 5. T-301 Metadata Harvester per run

**Spec:** FR-005, §8.3, `MetadataInventory.json` (§10). **Depends on:** T-204, T-103.

### What was built
`POST /runs/{id}/harvest` reads every table of the run's scoped Lakehouse and schemas (columns, types, nullability, descriptions where the API gives them) and saves the inventory. Body `{"schemas"?: [str]}` (default `scope.schemas`, or all schemas if those are empty). Response `{"summary": {tables, columns, errors}, "artifact": ArtifactItem, "warnings": [...]}`. `GET /runs/{id}/inventory` returns the current file (`404 NOT_FOUND` before the first harvest; the response uses the alias `schema` for a table's schema).

| File | Role |
|---|---|
| `app/discovery/harvester.py` | `resolve_schemas`, `harvest_tables`, `classify` / `to_fabric_error` (HTTP errors to codes); no schema or table name in code |
| `app/workflow/harvest_stage.py` | `harvest_run` (state check, versioning, files, artifact registration), `save_inventory`, `load_inventory`, `ScopeMissing`, `canonical_hash`, `write_json` |
| `app/contracts/metadata_inventory.py` | Pydantic models of the file (`MetadataInventory`, `InventoryTable`, later also the profile and relationship models) |
| `app/connectors/fabric_lakehouse.py` | `list_tables` now follows `next_page_token` (a repeated token stops the loop); the debug print of the whole response was removed from it |
| `app/api/schemas.py`, `app/api/runs.py`, `app/api/errors.py` | request and response shapes, routes, `ScopeMissing` to `400 BAD_REQUEST` |
| `app/manual_tests/t301_offline_checks.py` | offline checks with a fake Lakehouse |

### How it was built, in order
1. Read the task, `CONTRACTS.md` and the existing `metadata_inventory.py`, `fabric_lakehouse.py`, `scope.py` (the scope-lock rule already looks for an artifact named `MetadataInventory`), `compile_stage.py` (to copy its stage-service shape and reuse `WrongState`).
2. Added paging to `list_tables`.
3. Wrote the models, then `harvester.py`, then `harvest_stage.py`, then the routes, then the offline checks.
4. Ran the offline checks of T-102/T-103/T-204/T-205 for regressions; updated `CLAUDE.md`, `MANUAL_TESTING.md`, the README row.

### Rules
- Allowed in `REQUIREMENT_APPROVED`, and in `DATA_PROFILED` for a re-harvest, which moves the run back to `REQUIREMENT_APPROVED` (`409 WRONG_STATE` otherwise). A run with no scope is `400 BAD_REQUEST`.
- The body's `schemas` overrides `scope.schemas` for that harvest only; the run's scope is not changed. Names are matched ignoring case and saved as the Lakehouse spells them. An unknown schema is `404 SCHEMA_NOT_FOUND` and nothing is written; a failed listing aborts with a typed Fabric error (`403`, `429`, `504`, `502`) and nothing is written.
- A table that fails is **left out of `tables`** and listed in the inventory's `errors[]` (`FORBIDDEN`, `NOT_FOUND`, `RATE_LIMITED`, `UPSTREAM_TIMEOUT`, `UPSTREAM_ERROR`); the others are still harvested. A table with no columns is kept with `columns: []` and a table-level `NO_COLUMNS` error (also listed in `errors[]`). Zero tables gives an inventory with `tables: []` and a warning in `warnings[]` (an addition to the task's file shape).
- Version = highest of the existing version files and the registered artifact, plus 1. The artifact is registered with status `draft` and `based_on: {BusinessContract: <hash>}`. Progress is logged every 50 tables (`app.discovery.harvester`). Tables are sorted by `(schema, table)` ignoring case; names are otherwise preserved exactly (spaces, Unicode).
- A new version has `profile: null` and `relationship_evidence: []`, which is how "re-harvest invalidates profiles and evidence" is implemented.

### Steps to test
1. Setup, then get a run to `REQUIREMENT_APPROVED` with scope `saleslt` (run A) and another with no schemas (run B).
2. `POST /runs/{run_A}/harvest` (no body). Expect 200 with `summary` and `artifact` (`MetadataInventory`, version 1). Open `runs\<run_A>\MetadataInventory.json`: every `saleslt` table is listed and the summary counts match the file; `GET /runs/{run_A}/inventory` returns the same.
3. Pick three tables and compare columns and types with the Lakehouse explorer in Fabric.
4. `POST /runs/{run_B}/harvest` with `{"schemas": ["nexora_test"]}`. Expect the five fixture tables; run B's own scope is unchanged.
5. Harvest a run in `CREATED`: `409 WRONG_STATE`. Harvest run A with `{"schemas": ["no_such_schema"]}`: `404 SCHEMA_NOT_FOUND`, file unchanged.
6. Harvest run A again: `version` is 2, `GET /runs/{run_A}/artifacts` shows the new hash, `inventories\` holds `.v1.json` and `.v2.json`. `PUT /runs/{run_A}/scope` now gives `409 SCOPE_LOCKED`.
7. Offline: `python -m app.manual_tests.t301_offline_checks` (expects `All checks passed.`).

## 6. T-302 Generic data profiler

**Spec:** FR-006, NFR-008, §14. **Depends on:** T-301.

### What was built
`POST /runs/{id}/profile` with an optional body `{"tables": ["schema.table"]}` returns `{"profiled", "warnings", "errors"}` (profiled = ok or warning, errors = status `error`). It profiles the **candidate tables** (harvested tables whose name matches a contract entity) plus any tables the body names, over the Lakehouse SQL endpoint, and writes each `TableProfile` into `tables[].profile`.

| File | Role |
|---|---|
| `app/discovery/data_profiler.py` | `profile_tables(connector, inventory, tables)`, `candidate_tables`, `quote_identifier`, `column_kind`, `classify_error`; the old `profile_product_ids` prototype stays because `app/test_data_profiler.py` uses it |
| `app/workflow/profile_stage.py` | `profile_run` (state check, candidates plus named tables, merge, save) |
| `app/contracts/metadata_inventory.py` | `TableProfile`, `ColumnProfile`, `Freshness`, `ProfileEvidence` |
| `app/connectors/fabric_sql_connector.py` | optional `token_provider` (OBO) on the constructor and on `for_scope` |
| `app/api/deps.py` | `get_sql_connector_factory` |
| `app/manual_tests/t302_offline_checks.py` | offline checks; a fake SQL cursor evaluates the profiler's own SELECTs against in-memory tables |

### How it was built, in order
1. Read the task, `data_profiler.py` (hardcoded prototype), `fabric_sql_connector.py` (interactive credential only) and `requirement_data_matcher.py`.
2. Gave the SQL connector a token provider, added the OBO dependency.
3. Extended the models, wrote the profiler (one `COUNT_BIG(*)`, then aggregate queries of up to 20 columns each, then one duplicate query per non-unique key), then the stage and route.
4. Wrote the offline checks around a fake cursor; ran all earlier checks.

### Rules
- Allowed in `REQUIREMENT_APPROVED` and `DATA_PROFILED`; the run state never changes (T-304 does that). Needs a harvested inventory (`404 NOT_FOUND`) and a scope with a SQL endpoint (`400 BAD_REQUEST`). A named table not in the inventory is `404 NOT_FOUND`; a malformed name (no single dot) is `422`.
- Per column: `null_count`, `distinct_count`, `is_key_candidate` (name ends in `ID` or `Key`), `is_unique` (key candidates only: `distinct == rows - nulls`, `null` when approximate), `duplicate_count` (the number of values that appear more than once, exactly what `GROUP BY ... HAVING COUNT(*) > 1` returns; this is what the T-004 check compares), `min`/`max` (date and numeric columns only, dates as `YYYY-MM-DDTHH:MM:SSZ`), `approximate`, `note`. Column types that can't be counted (binary, arrays and the like) are skipped with a note.
- Above 10 million rows: `APPROX_COUNT_DISTINCT` and `approximate: true`. Empty table: `row_count: 0`, warning "The table is empty", uniqueness `null`. A column that is entirely null warns; a key column with nulls warns; a non-unique key warns "X is not unique (n duplicate values)".
- Freshness: the date column whose name hints at it (modified, updated, refresh, load, ingest, created), else the first date column; `status` is `ok` or `unknown` and `age_days` is given. There is no staleness threshold (the task named none).
- A table that fails gets `status: error` with `code` (`TABLE_NOT_FOUND`, `QUERY_TIMEOUT`, `QUERY_FAILED`); the others continue. A connection failure is `502 UPSTREAM_ERROR`.
- Profiles are merged with earlier ones, then the file and its same-version copy are rewritten and the artifact hash changes (version unchanged).
- At the end of this task candidate matching used the old `ALIASES` dict of the matcher (with a lookup by lower-cased entity first, because its keys contain spaces). T-401 replaced that dict with `config/glossary.yaml`.

### Steps to test
1. Setup; run A harvested for `saleslt` with an entity that matches products (prompt `Show total sales by product`), run B harvested for `saleslt` and `nexora_test`.
2. `POST /runs/{run_A}/profile` with `{"tables": ["saleslt.SalesLT_Product"]}`. Expect 200 and counts. In the SQL endpoint run `SELECT COUNT(*) FROM saleslt.SalesLT_Product`: it equals `row_count` in `GET /runs/{run_A}/inventory`. `columns.ProductID` has `is_unique: true` and `distinct_count` equal to `row_count`.
3. `POST /runs/{run_B}/profile` with `{"tables": ["nexora_test.dim_product_dupes"]}`. Expect `ProductID.is_unique: false`, table `status: warning`, a warning with the duplicate count; run `SELECT ProductID, COUNT(*) c FROM nexora_test.dim_product_dupes GROUP BY ProductID HAVING COUNT(*) > 1`: the number of rows equals that count (at least 3).
4. Compare a date column's `min`/`max` with `SELECT MIN(col), MAX(col)`.
5. Search `runs\<run_A>\MetadataInventory.json` for a real product name (`Select-String`): no match.
6. `{"tables": ["saleslt.NoSuchTable"]}` is `404`; profiling a `CREATED` run is `409 WRONG_STATE`; re-harvest clears the profiles.
7. Offline: `python -m app.manual_tests.t302_offline_checks`.

## 7. T-303 Relationship evidence

**Spec:** FR-007, §9 (Relationships row), business rule 7. **Depends on:** T-302.

### What was built
`POST /runs/{id}/relationships/analyze` returns `{"candidates", "high", "medium", "low", "rejected", "warnings"}` (`candidates` counts the non-rejected ones, so it equals `high + medium + low`). `GET /runs/{id}/relationships` returns the list (`[]` before the first analysis). Each `RelationshipEvidence` has `id` (`R1...`), `from`/`to` (`{table: "schema.table", column}`), `source` (`heuristic`, `llm`, `user`), `type_compatible`, `overlap_pct`, `orphan_rate`, `null_rate`, `cardinality`, `confidence`, `thresholds`, `evidence {queries, computed_at}`, `status` (`candidate`/`rejected`), `rejected_reason` and `notes`.

| File | Role |
|---|---|
| `app/discovery/relationship_candidates.py` | heuristic candidates, the model's candidates (`llm_candidates`, strict JSON schema, `default_relationship_llm`), `Candidate` |
| `app/discovery/relationship_evidence.py` | `measure`, `resolve`, `types_compatible`, `load_thresholds` |
| `app/workflow/relationship_stage.py` | `analyze_run` (candidates, profile what is missing, measure, save), `summarize`, `list_relationships` |
| `config/relationship_thresholds.yaml` | `high: {orphan_rate_max: 1.0, overlap_pct_min: 99.0}`, `medium: {orphan_rate_max: 10.0}`, `require_unique_target: true` |
| `app/contracts/metadata_inventory.py` | `RelationshipEvidence`, `ColumnRef`, `RelationshipQueryEvidence` |
| `app/api/deps.py` | `get_relationship_llm` (a separate dependency from `get_llm`, so the schema name sent to the model is its own) |
| `app/manual_tests/t303_offline_checks.py` | offline checks; fake SQL and fake model; imports and extends the `t302` fixtures |

### How it was built, in order
1. Read the task, the old `semantic_mapper.py` and `relationship_validator.py` (the old validator raises on a hallucinated name; the task wants it rejected with a reason, so it was not reused), `structured.py` and how `compile` injects the model.
2. Wrote the candidate generators, then the evidence rules, then the stage, then routes and request body, then the checks.

### Rules
- **Candidates:** (1) heuristic: a column `XxxID` in table A to a column `XxxID` (else `ID`) in a table B whose underscore-separated name contains `Xxx` as a whole word (singular and plural), B different from A, only in the same inventory; (2) the model, which sees the contract summary and table and column names and types; (3) the optional request body `{"candidates": [{"from": {"table","column"}, "to": {...}}]}`, which gives `source: user` (this is how the task's "add one by hand" works). The same join twice is kept once (first source wins). At most 200 candidates are analyzed, with a warning.
- **Rejections:** a table or column not in the inventory (`table not in inventory`, `column not in inventory`; a bare table name is accepted if it is unique), a self-relationship (same table and column), a table that can't be profiled (`profile missing`), a failed evidence query (`evidence query failed (<code>)`). Tables a candidate uses are profiled first if they have no profile.
- **Type compatibility:** same family (integer, decimal, string, date, boolean), or integer with decimal. A mismatch runs **no** join query: `type_compatible: false`, `confidence: low`, no numbers.
- **Evidence queries** (aggregate-only, two per candidate): overlap over distinct non-null source values against the distinct target keys, and the orphan count over source rows. `orphan_rate` equals what `python -m app.test_product_mapping` derives (`(detail_rows - matched_rows) / detail_rows`).
- **Cardinality:** target unique and source unique `one_to_one`; target unique only `many_to_one`; target not unique `many_to_many` (a note says so, also when the source is unique).
- **Confidence:** a type mismatch or (with `require_unique_target`) a non-unique target is `low`; otherwise `high` if orphan rate and overlap meet the high thresholds, `medium` if the orphan rate meets the medium one, else `low`.
- **A failing model** (timeout, content filter, upstream error, unusable output) does not fail the call: the heuristic and user candidates are still analyzed and `warnings` says the suggestions were skipped. An invalid `config/relationship_thresholds.yaml` is `500 CONFIG_ERROR` before any query or model call.
- Evidence replaces the previous list; the file and the artifact hash are updated, the version is not. State must be `REQUIREMENT_APPROVED` or `DATA_PROFILED`; the state never changes. Same preconditions as T-302 (`404`, `400`).

### Steps to test
1. Setup; run A harvested for `saleslt`, run B harvested for `saleslt` and `nexora_test`.
2. `POST /runs/{run_A}/relationships/analyze` (no body). In `GET /runs/{run_A}/relationships` find `saleslt.SalesLT_SalesOrderDetail.ProductID` to `saleslt.SalesLT_Product.ProductID`: `many_to_one`, `high`, `source: heuristic`; its `orphan_rate` equals the one computed from `python -m app.test_product_mapping`.
3. Analyze again with `{"candidates": [{"from": {"table": "saleslt.SalesLT_SalesOrderDetail", "column": "ProductID"}, "to": {"table": "saleslt.SalesLT_Customer", "column": "CustomerID"}}]}`: that entry is `source: user`, `confidence: low`, with a small `overlap_pct`. A candidate `SalesLT_Product.Name` to `SalesLT_Customer.CustomerID` gives `type_compatible: false` and no queries. A candidate with a column that doesn't exist is `status: rejected`, `rejected_reason: "column not in inventory"`.
4. `POST /runs/{run_B}/relationships/analyze`: entries whose `to.table` is `nexora_test.dim_product_dupes` are `many_to_many`, `low`, with the "not unique" note.
5. Open `runs\<run_A>\MetadataInventory.json`: `relationship_evidence` holds the entries and the profiles of the tables used. Re-harvest: the list is `[]` again.
6. Offline: `python -m app.manual_tests.t303_offline_checks` (this is also where a model-suggested hallucinated column is exercised).

### Rules
- **Candidate tables** = harvested tables whose name matches a contract entity, plus matching tables that **failed to harvest** (so an inaccessible table can't be skipped). No candidates fails G2.1 with "no candidate tables matched the contract".
- **Checks** (deterministic): G2.1 every candidate is accessible (no harvest error, no profile error; evidence lists the candidates); G2.2 columns and types present; G2.3 a profile exists; G2.4 profile warnings summarized (`warning`, never `fail`); G2.5 every non-conformed candidate has an approved exception (`missing_exceptions`, `excepted` in the evidence). The result is saved as `runs/<id>/gates/G2-<timestamp>.json` with artifact `MetadataInventory` and the inventory artifact's hash. Relationship evidence is shown on the screen but is not part of any check (the task's check table has none).
- **Exceptions:** `POST /runs/{id}/exceptions` `{"table", "rationale"}`, role `data_engineer` (`403`), state `REQUIREMENT_APPROVED` only (`409 WRONG_STATE`), the table must be a candidate (`422`; the name is matched ignoring case and saved canonically), rationale 1 to 2000 characters. Response `201 {"exception_id", "table", "approved_by", "at"}`. It is an approval record in `approvals.jsonl` with artifact `Exception:<schema.table>`, action `ACCEPT`, the rationale as `comment`.
- **Accept of the inventory:** `POST /runs/{id}/approvals` with `{"artifact": "MetadataInventory", "action": "ACCEPT", "expected_hash": <hash of the MetadataInventory artifact>, "comment"?}`. Needs role `data_engineer` (the task named no role; this is a decision of this session), state `REQUIREMENT_APPROVED`, a current hash (`409 STALE_VERSION`) and a passing G2 (`409 GATE_FAILED`, with `failed_checks`). It marks the artifact `approved`, moves the run to `DATA_PROFILED`, appends an `ACCEPT` record with `gate_result_ref`. Any other action on the inventory is `422`. Accepting twice is `409 WRONG_STATE`.
- **Re-harvest after Accept** (T-301) returns the run to `REQUIREMENT_APPROVED` with a draft inventory and no profiles, so G2 must be run again.
- **Data gaps:** `POST /runs/{id}/data-gaps` `{"description"}`, any signed-in user, states `REQUIREMENT_APPROVED` and `DATA_PROFILED`. Appends `{gap_id, description, raised_by, at, from_state}` to `runs/<id>/data_gaps.jsonl`, moves the run to `NEEDS_INPUT` (`resume_state` kept, the description is in the history reason), returns `RunDetail` whose `data_gaps` lists them. The other two failure actions are re-harvest and "narrow the scope" (a re-harvest with a `schemas` list).
- **UI:** the page loads the run, `/me`, approvals, the inventory and a fresh G2 check. Buttons: Harvest or Re-harvest, Profile candidates, Analyze relationships, narrow the scope, Raise data gap, Accept (disabled with the reason from `acceptBlockedReason`), Approve exception (shown to a `data_engineer`). The table list has a search box and 50 per page; each warning has "Show evidence" (the numbers of its column and the SQL that ran); each relationship has "Show SQL". Every approval sends `expected_hash` from the run's artifacts; a stale hash shows "The inventory changed. Reload". All decisions come from the API; the UI holds no gate logic.

## 9. Gotchas learned in this session

- **Offline checks that call the API must override `get_runs_root`** (as well as `get_store`), otherwise the stage writes into the real `runs/` folder. One check did this once; its folder was deleted.
- **Fixtures chain:** `t303` and `t304` import `t302`'s module and change its globals (`LAKEHOUSE`, `DATA`, `ERRORS`). Don't run them in one process after other fixtures changed; re-run all of `t301` to `t304` after editing a fixture.
- **CRLF files:** many files in the repo are CRLF, and `.claude/MANUAL_TESTING.md` also contains stray lone CR characters inside some lines. A script that reads and writes it in text mode with universal newlines silently changes those lines. Read and write with `newline=""`, detect `\r\n`, and check `git diff` shows only your lines.
- **Windows and Git Bash:** `/tmp` in Git Bash is not the same path for `.venv\Scripts\python.exe`; use real Windows paths (or the session scratchpad) for helper scripts.
- **Profiles and evidence change the artifact hash, not the version.** The UI and the approval API must use the artifact's *current* hash as `expected_hash`; after profiling, a hash read before is stale.
- **Percentages are 0-100**, not fractions; thresholds are in the same unit.
- **A table that failed to harvest is not in `tables`.** Code that needs "all candidate tables" must also look at `inventory.errors` (G2 does, through `candidate_error_tables`).
- **The inventory file uses the key `schema` for a table's schema** (the model field is `schema_name`, serialized by alias). Dump with `by_alias=True` (`MetadataInventory.to_dict()`).
- **`list_schemas` in `fabric_lakehouse.py` still prints a debug dump of the response**; only `list_tables` had its print removed.
- A bad `config/relationship_thresholds.yaml` or `config/conformed_sources.yaml` only shows as `500 CONFIG_ERROR` when the stage that reads it runs (it is not checked at API start like `roles.yaml`).

## 10. Open follow-ups (as of the end of the session)

- **Who accepts the inventory** was decided as `data_engineer` (the task named no role). Change `DATA_ROLE` in `inventory_review.py` and the UI's `DATA_ROLE` in `src/lib/inventory.ts` together if that should differ.
- **Relationship evidence is not part of G2.** If a reviewer should be blocked by rejected or low-confidence relationships, add a check to `run_g2`.
- **Exceptions are per table, not per inventory version.** An exception stays valid after a re-harvest. Bind it to a hash if that is not wanted.
- **Heuristic joins are strict** (`XxxID` to a table named for `Xxx`): `SalesOrderID` does not pair with `SalesOrderHeader`. The model or a hand-added join covers those.
- **Harvest and profiling are sequential**; a Lakehouse with several hundred tables takes a while. Concurrency was not added.
- **Leaving `NEEDS_INPUT`:** at the end of this session nothing in the API left `NEEDS_INPUT` after a data gap (the CLI `python -m app.cli runs transition RUN_ID STATE` does). Check `CLAUDE.md` for what later tasks changed.
- The profile's freshness has no staleness threshold (`ok` or `unknown` plus `age_days`).
