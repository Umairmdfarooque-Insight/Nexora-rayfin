## 1. The goal of M6 and the pipeline

M6 turns an approved semantic model into a reviewed Power BI report, with the same rules as the rest of Nexora: the LLM proposes, deterministic code validates and decides, nothing is invented, and every approval is tied to a hash.

```
MODEL_APPROVED
  POST /runs/{id}/report/plan        T-601  ReportPlan.json (unanswered questions -> data gap -> NEEDS_INPUT)
  POST /runs/{id}/report/generate    T-602  report/v<n>/ (PBIR) published to the sandbox -> REPORT_GENERATING
REPORT_GENERATING
  POST /runs/{id}/report/validate    T-603  Gate G5 entry in ValidationReport.json
      all checks pass  -> stays REPORT_GENERATING
      a check fails    -> REPORT_FAILED -> POST /report/repair -> REPORT_GENERATING | NEEDS_INPUT
      a model defect   -> REPORT_FAILED -> MODEL_GENERATING (a failed G4 entry is recorded)
  GET  /runs/{id}/report/review      T-604  rendered pages, per-visual status, approvals
  POST /runs/{id}/approvals {artifact: "Report", action: ACCEPT | REJECT | REGENERATE}   T-604
      both roles accept on the current hash and G5 passes -> REPORT_APPROVED
```

Run-state transitions used (all already in `app/workflow/states.py`, none were added): `MODEL_APPROVED -> REPORT_GENERATING`, `REPORT_GENERATING -> REPORT_FAILED | REPORT_APPROVED`, `REPORT_FAILED -> REPORT_GENERATING | MODEL_GENERATING`, any state `-> NEEDS_INPUT`. A model defect needs **two** transitions (`REPORT_GENERATING -> REPORT_FAILED -> MODEL_GENERATING`) because the table has no direct edge.

|---|---|---|

## 2. The steps of a task (the loop used for every task)

1. `/implement-task T-xxx`: read `.claude/CLAUDE.md`, `.claude/tasks/README.md` and the task section; check that the tasks it depends on are `Done`; if the task is under "First needed at" in the README's decisions table, ask the user (only T-602 was: the report authoring route).
2. `git fetch`, `git switch main`, `git pull --ff-only`, then `git switch -c task/T-xxx-<slug>` (slug: at most 5 words, `[a-z0-9-]`). Put the branch name in the README's Branch column and set the status to `In progress`.
3. Read the existing code the task extends (the closest earlier stage is the template) and the Microsoft docs the task says to check (PBIR, T-602 and T-603).
4. Implement, matching the surrounding style; add the offline script `app/manual_tests/t<NNN>_offline_checks.py` with fakes for the model, Fabric and Power BI.
5. Run the new script, then the scripts of the stages the change touches (see "Running the checks").
6. Hand over: update `.claude/CLAUDE.md` (a section for the task), add the task's section to `.claude/MANUAL_TESTING.md` and the script to its helper table, set the README status to `Awaiting manual test`.
7. After the manual test: `/implement-task done T-xxx` (status `Done`), `/commit-push` (commit message with Tasks, Changes, Notes and the attribution line; secrets, large files and generated files are checked first), open the PR, then `/cleanup-branch` (switch to `main`, pull, delete the branch locally and on GitHub after confirmation).

Rules that apply to every task: hybrid orchestration (the run state machine and `RunStore` own state; a LangGraph graph never changes state or writes `RunManifest.json`); the LLM proposes and code decides; no silent KPI assumptions; Data Gap instead of a fabricated calculation; never send raw rows to the model; never read or print `.env`; deploy only to the sandbox.

## 3. T-601 Report planner

**Goal:** a reviewable `ReportPlan.json` (questions, pages, visuals, filters, drill, interactions) from the approved contract and ModelSpec, where every referenced object exists in the ModelSpec.

### Steps taken
1. Read `measure_stage.py`, `dax_generator.py`, `llm_cache.py`, `llm/structured.py`, `contracts/model_plan.py`, `inventory_review.raise_data_gaps` and the `/model/measures` route: the DAX stage was the template (strict-JSON-schema model call, code validation, answer cache, versioned file, artifact registration).
2. `app/contracts/report_plan.py`: pydantic models with `extra="forbid"` (`ReportPlan`, `Page`, `Visual`, `VisualFields`, `FieldRef`, `Filter`, `Drill`, `Question`, `Interaction`, `UnansweredQuestion`) and `to_data`, which drops unused keys of a field reference (so a field is `{"measure": ...}`, `{"table", "column"}` or `{"table", "hierarchy"}` in the file).
3. `app/report/plan_validation.py`: `validate_report_plan(data|plan, spec)` returns the parsed plan and a `GateResult` (`gate: REPORT.PLAN`) with checks RPLAN.1 to RPLAN.7:
   - RPLAN.1 schema; RPLAN.2 references exist (measure with DAX, column, hierarchy, filter column; `values` must be measures, never raw columns); RPLAN.3 every question is on a visual or listed unanswered; RPLAN.4 unique visual ids and page names; RPLAN.5 supported visual types (`card, lineChart, clusteredBarChart, clusteredColumnChart, tableEx, pivotTable, slicer`, the failure lists them); RPLAN.6 at most 8 visuals per page; RPLAN.7 interactions point at existing visuals and use `filter | highlight | none`.
   - Every failure names its path, for example `v1.fields.values[0]: measure 'Net Revenue X' is not in the approved model`.
4. `app/report/planner.py`:
   - `derive_questions` (by code): `Q-R<n>` for each contract KPI (trend question when it has `time_logic`, else "What is X?") then one per dimension; a KPI with no measure that has DAX goes in `forced` (unanswered up front, the model is not asked); if every question is forced there is no model call.
   - `derive_audience`: roles of `contract.security[].applies_to`, else "<subject area> stakeholders".
   - `llm_schema()` (strict JSON schema), `build_payload` (objective, KPIs, dimensions, questions, measures with DAX, tables with non-hidden columns and hierarchies: names and types only), `SYSTEM_PROMPT`.
   - `propose_report_plan`: up to 2 attempts; the second carries the failures; a visual that maps a forced question is also an error; after success `_finalize` renumbers visual ids `v1..` in page order, remaps interactions and sets `unanswered_questions` = forced + the questions the model declared that really have no visual.
5. `app/workflow/report_plan_stage.py`: `generate_report_plan` (state `MODEL_APPROVED` else `409 WRONG_STATE`; needs the approved ModelSpec and TMDLModel `404`, ModelSpec hash still the approved one `409 STALE_VERSION`, and the contract). Writes `ReportPlan.json` and the versioned copy, keeps the version when nothing changed (compares ignoring `version`), registers the artifact (`needs_input` if unanswered, else `draft`) with `based_on = {SemanticModel: <TMDLModel hash>, BusinessContract: <hash>}`, caches the accepted model answer (`CachedLlm`), and for unanswered questions calls `raise_data_gaps(..., states=(MODEL_APPROVED,))`, which moves the run to `NEEDS_INPUT`. `read_report_plan` re-validates the saved file for `GET`.
6. `inventory_review.raise_data_gaps` got an optional `states` argument (default unchanged).
7. API: `POST` and `GET /runs/{id}/report/plan` (`ReportPlanResponse {plan, validation, run}`), dependency `get_report_llm`; CLI `python -m app.cli report validate runs/<id>` (`VALID`/`INVALID`, exit 0/1/2).
8. Offline script `t601_offline_checks.py`; docs.

### Decisions
- Questions and unanswered handling are code, not model output. The model can only declare a question unanswered, never answer it with another measure.
- `based_on.SemanticModel` is the `TMDLModel` artifact hash (the task did not say which artifact).
- Dropping a question needs a contract change (a return, T-701): re-planning a plan with an unanswered question moves the run back to `NEEDS_INPUT`.
- Adding a visual type means three edits: `contracts/report_plan.py:VISUAL_TYPES`, the planner prompt/schema, and `report/pbir_generator.py:ROLES`.

### Errors
`409 WRONG_STATE`, `404 NOT_FOUND` (no approved model, no plan for `GET`), `409 STALE_VERSION`, `502 LLM_INVALID_OUTPUT` (unusable twice; nothing saved).

## 4. T-602 PBIR generator and sandbox publish

**Goal:** a deterministic PBIR folder generated from the plan, bound by connection to the deployed model and published to the sandbox, versioned per run.

### Steps taken
1. The user was asked to confirm the open decision "report authoring route" (default: deterministic PBIR generator). Answer: deterministic generator; recorded in the README decisions table.
2. Read Microsoft's PBIR and Fabric report-definition documentation (folder layout, `definition.pbir` v2 with `byConnection` and `semanticmodelid=<id>`, `report.json` 3.1.0, `versionMetadata` 1.0.0, `pagesMetadata` 1.0.0, page 2.0.0, visualContainer 2.0.0; create/update with `format: PBIR` and `InlineBase64` parts).
3. `app/report/pbir_generator.py`:
   - `SCHEMAS` constants; `ROLES` maps the plan's roles to PBIR query roles (card: Values; line, bar, column: Category/Series/Y; tableEx: Values; pivotTable: Rows/Columns/Values; slicer: Values).
   - Fields: a measure is a `Measure` expression with its **home table** from the ModelSpec; a column a `Column`; a hierarchy becomes one `HierarchyLevel` projection per level, the first `active: true`, the others reachable by drilling.
   - Filters are categorical `In` filters with literals (`2024L` integer, `2.5D` float, `'text'` with doubled quotes); page filters go in `page.json`, visual filters in `visual.json`.
   - Layout: page 1280x720, margin 16, a grid (1 column for one visual, 2 up to four, else 3), z and tab order `i*1000`.
   - Interactions go in the source page's `visualInteractions` (`filter/highlight/none` -> `DataFilter/HighlightFilter/NoFilter`); both visuals must be on the same page.
   - Page folders `p<n>` in plan order (name = folder), visual folders = the plan's ids. Output is byte-identical (fixed key order, `ensure_ascii=False`, two-space indent, LF).
   - Failures raise `PbirGenerationError` naming the visual before any file is written: unsupported type, drill on a non-chart or a hierarchy that isn't a category field, card without a measure, slicer without a field, empty page, interaction across pages.
   - `check_pbir(folder)`: required keys, exact `$schema`, names matching `^[\w-]{1,50}$`, `pageOrder` equals the page folders, unique visual names.
4. `app/deploy/fabric_items.py`: `pbir_parts(dir)` (`definition.pbir` then `definition/**`) and `FabricItemsClient.upsert_report(workspace_id, display_name, pbir_dir)` through the existing `_upsert` (so the sandbox guard, same-name detection, `NameConflict`, 202 polling and 429 retry are shared with the model).
5. `app/workflow/report_stage.py:generate_report`: state `MODEL_APPROVED` or `REPORT_GENERATING`; loads and re-validates the plan (`ReportPlanInvalid` -> `422` with the failures; unanswered questions -> `422`); `plan.based_on.SemanticModel == TMDLModel hash` else `409 STALE_VERSION`; sandbox workspace from `get_sandbox_workspace_id` (`500 CONFIG_ERROR`); looks up the model `Nexora_<run id[:8]>` by name (`ModelNotDeployed`, a `NotFound`); generates and runs `check_pbir` in `report/.v<n>.tmp`; `upsert_report` from the staging folder; only then renames to `report/v<n>/`; writes `ReportPublish.json`; registers `PbirReport` (`draft`, `based_on` plan hash + model hash, hash = `folder_digest`); moves `MODEL_APPROVED -> REPORT_GENERATING`.
6. API `POST /runs/{id}/report/generate` (`ReportGenerateResponse {version, files, report_item_id, operation, run}`), error handler `ReportPlanInvalid -> 422 VALIDATION_ERROR`.
7. Offline script `t602_offline_checks.py` (reuses `t601` helpers and `t501.FakeFabric`); docs.

### Decisions
- `generate_pbir(plan, model_item_id, out_dir, spec)` has the ModelSpec as a fourth argument (the task signature had three) because a measure reference needs its table.
- The report is named `Nexora_<run id[:8]>_Report`: the model's name is taken and `_upsert` raises `NameConflict` for a same-named item of another type.
- Every call writes the **next** version, even when nothing changed (v1 and v2 are identical, which is the determinism property).
- Publishing happens before the rename and the state move, so a Fabric failure leaves no version and no state change.

### Known unverified details
Two things come from Microsoft's examples and were not validated against the live JSON schemas: `visualInteractions` in `page.json` and the visual title under `visual.visualContainerObjects`. If Fabric rejects a file its message names it; the fix is in `pbir_generator.py`.

### Errors
`409 WRONG_STATE`, `404` (no plan, no approved model, model not in the sandbox), `409 STALE_VERSION`, `422 VALIDATION_ERROR` (plan invalid, generation error, unanswered questions), `500 CONFIG_ERROR`, `403 TARGET_NOT_ALLOWED`, `409 NAME_CONFLICT`, `502 UPSTREAM_ERROR` (Fabric rejects the definition; its message and request id are kept).

2. **Shared validation file.** `ValidationReport.json` now holds both artifacts' entries. Added `ValidationReport.runs_of(artifact)` and `.latest(artifact)`; changed the model's readers to ask for `SemanticModel` (`repair/service.py`, `workflow/model_review.py`, `workflow/bridge_model_stage.py` baseline, `validate_stage.py` attempt counter and `register_report`, whose `based_on` key is `PbirReport` for a report entry).
3. `app/report/pbir_generator.py`: split `generate_pbir` into `build_files(plan, model_id, spec) -> {relative path: data}` plus writing; added `file_bytes` and `folder_digest` (hash of every file except `renders/`).
4. `app/report/pbir_reader.py`: reads pages, visuals, bound fields (`measure | column | hierarchy | unsupported`, with `active`) and filters (with literal parsing) from the files on disk.
5. `app/connectors/powerbi_api.py`: `ExportUnavailable` and `PowerBiClient.export_report_page(ws, report_id, page, timeout_s)`: `POST .../ExportTo {"format": "PNG", "powerBIReportConfiguration": {"pages": [{"pageName": ...}]}}` (400/403/404 -> `ExportUnavailable`), poll `.../exports/{id}`, download `.../file`; `FabricTimeout` if it doesn't finish. One page per export, so each result is a single PNG.
6. `app/report/validators.py`: `object_of(rel)` maps a file to `visual:<id>`, `page:<name>` or `report`; the four checks (below); `build_query` for a visual.
7. `app/workflow/report_validate_stage.py`:
   - `ReportEnvironment`, `run_report_validation` (SCHEMA + BIND on the files; QUERY against the model's current item id; publish and RENDER only if SCHEMA and BIND pass, a visual with a failed binding has its query `skipped`, pages are `skipped` when not published; appends a `Report` entry; a `FILES_CHANGED` warning when the files differ from the registered hash).
   - `validate_report` (state `REPORT_GENERATING`) and `settle` (register the validation artifact, then: pass keeps the state, a failure moves to `REPORT_FAILED`, a model defect continues to `MODEL_GENERATING`).
   - `route_model_defects`: records a **failed `G4.DAX` entry** (`code REPORT_QUERY_FAILED`, evidence `routed_from: G5.QUERY`) for the current model hash, registers it, then transitions `REPORT_FAILED -> MODEL_GENERATING` with the reason "Model defect found by report validation: ...".
8. `app/repair/report_adapter.py` (`ReportRepairAdapter`) implements the same adapter interface as the model's, so `graphs/repair.py` is unchanged: `classify` (`report_repair_code`: `REPORT_STRUCTURE` for object `report`, `REPORT_SCHEMA`, `REPORT_BINDING`, `REPORT_QUERY`), `deterministic_fix` (regenerates the file of each failing visual/page from the plan into a staging **copy of the current version without renders**), `has_changes`, `scope_guard` (allowed files = the failing objects' files), `validate` (next `report/v<n>`, publish, validate with `repair_attempt`).
9. `config/repair_policy.yaml`: `REPORT_BINDING: deterministic`, `REPORT_SCHEMA: deterministic`, `REPORT_STRUCTURE: user_input`, `PUBLISH_FAILED: user_input`.
10. `repair/service.py`: `REPAIR_STATES` has `Report: (REPORT_FAILED,)`; `repair(..., "Report")` calls `repair_report`: runs the generic graph once, registers `PbirReport` and the validation artifact after it, then one transition: passed -> `REPORT_GENERATING`; a remaining model defect -> `MODEL_GENERATING`; anything else -> `NEEDS_INPUT` (`resume_state REPORT_FAILED`). The model arguments (`llm`, SQL factory, recon LLM) became optional.
11. API `POST /runs/{id}/report/validate` (`ReportValidateResponse {report, run}`) and `POST /runs/{id}/report/repair` (`RepairResult`). Updated `t505_offline_checks` (it used to assert that repairing a `Report` is unsupported). Offline script `t603_offline_checks.py`; docs.

### The checks
| Check | What | Outcome |
|---|---|---|
| G5.SCHEMA | `check_pbir` (`$schema`, required keys, names); one check per problem, object = the file's visual/page/report | fail (defect `report`) |
| G5.BIND | every measure (bound to its own table, has DAX), column, hierarchy level and filter column exists in the ModelSpec; a visual with no field fails | fail (defect `report`) |
| G5.QUERY | per visual `EVALUATE` of `SUMMARIZECOLUMNS(group-by columns, TREATAS filters (page and visual), "name", [Measure]...)`, wrapped in `TOPN(100, ...)` when it groups; hierarchy contributes its active level's column | rows pass; zero rows = warning `NO_DATA`; `DaxError` = fail (defect `model`) |
| G5.RENDER | per page `export_report_page` into `renders/<page>.png` | pass; `RENDER_UNAVAILABLE` / `RENDER_TIMEOUT` = warning, never a pass; publish refused = fail `PUBLISH_FAILED` |

### Decisions
- Classification is stored in `evidence.defect` (`report` / `model` / null). `ValidationCheck.classification` (deterministic / llm / user_input) stays the repair policy's.
- A report is never published when SCHEMA or BIND fail, so a broken definition isn't pushed to Fabric.
- The extra failed G4 entry is the session's addition (not in the task text): without it the model's last passing validation would still look current after a model defect was found.
- `renders/` is excluded from the report hash and never uploaded (`pbir_parts` only sends `definition.pbir` and `definition/**`). A plain diff of two report versions after validation must skip `renders`.
- A plan that itself binds a missing object regenerates nothing: `no_progress`, escalated to the user.

### Errors
`409 WRONG_STATE` (also "Nothing to repair"), `404` (report not generated, model not in the sandbox), `500 CONFIG_ERROR`, upstream errors from Fabric or Power BI as `502`.

## 6. T-604 Report review and approval UI

**Goal:** a review screen (rendered pages, each visual's questions and statuses), regeneration of one visual or page with guidance, role approvals on the report hash, and a safe file endpoint for the images.

### Steps taken
1. Read `workflow/model_review.py` (the T-507 review and role approval), `approval.perform`, the model page `rayfin-ui/src/app/runs/[id]/model/page.tsx`, `lib/model.ts` and its tests, `api.ts`, `types.ts`: T-507 was the template.
2. `report_validate_stage.py`: extracted `settle(store, runs_root, run_id, entry, actor)` so validate and regenerate move the run the same way.
3. `app/report/regenerate.py`: `find_target(plan, page, visual)` (page matches the plan's name or `p<n>`); `regenerate_visual` and `regenerate_page` ask the model (strict schema, the reviewer's guidance, the part to replace) for a replacement, build a candidate plan (a replaced visual keeps its id and place; a page keeps its name, its visuals reuse the old ids in order, extra ones get new ids, interactions of removed visuals are dropped) and require the whole plan to pass RPLAN.1-7; one retry, then `RegenerationFailed` (an `LlmInvalidOutput`, `502`).
4. `app/repair/report_adapter.py`: added `regenerate(objects, prune_pages)` (writes the objects' files from the plan into the staging copy and removes visual folders the plan no longer has) and let `validate` take `None` as the repair attempt.
5. `app/workflow/report_review.py`:
   - `review()` builds `ReportReview` (page and visual details from the folder, the plan and the latest `Report` entry); `g5_gate` (checks of the latest entry plus `G5.CURRENT` when it is of another hash, `G5.VALIDATED` when there is none); `role_statuses` (pending, approved, rejected, invalidated); `approvals_done` with `current` and the note `invalidated: report changed`.
   - `decide_report`: Accept/Reject (role `project_reviewer` or `business_owner`) and REGENERATE; checks in the order action, role (422 / 403), state, hash, gate, "already approved"; both roles on the live hash move `REPORT_GENERATING -> REPORT_APPROVED` and mark `PbirReport` and `ReportPlan` `approved`.
   - `_regenerate`: loads plan, ModelSpec and contract; finds the target (`404`); asks the model; saves the plan as the next version; stages the new files with the adapter; no change -> nothing happens; scope guard violation -> `RegenerationOutOfScope` (`409 SCOPE_VIOLATION`); otherwise `adapter.validate` (publish and G5), registers the new `PbirReport` version and calls `settle`.
   - `ReportServices` dataclass: the model and **lazy** sandbox and Power BI client builders.
6. `workflow/approval.perform` routes `artifact == "Report"` to `decide_report` and gained `target` and `report_services` arguments. `api/schemas.py:ApprovalRequest` gained `target` and, **only for `artifact == "Report"`**, requires `target` and a comment for REGENERATE (applying it to the contract too broke the contract REGENERATE flow and was corrected). `api/deps.py:get_report_services`.
7. API `GET /runs/{id}/report/review` and `GET /runs/{id}/files/{path}` (`FileResponse`; absolute path, `..`, backslash, colon, directory, missing file or a path resolving outside the run folder is `404`; unknown run `404`; `Cache-Control: no-store`).

### Decisions and quirks
- The approval hash is the **live** `folder_digest`, so any change to the PBIR files (regeneration, repair, hand edit) invalidates earlier approvals. The registered `PbirReport` artifact hash is not updated by a hand edit: compare with `review()["report_hash"]`.
- A regeneration saves the new plan version **before** the files are regenerated and validated; if G5 then fails the plan stays at the new version. An identical replacement still bumps the plan version and records the REGENERATE approval.
- Regeneration needs the sandbox and Power BI clients (OBO). They are built only when a REGENERATE actually runs, so other approvals need no OBO configuration.
- Accept needs both roles; one user holding both roles approves in two separate actions.

### Errors
`409 WRONG_STATE`, `409 ALREADY_APPROVED`, `409 STALE_VERSION`, `409 GATE_FAILED` (names the failed checks), `409 SCOPE_VIOLATION`, `403 FORBIDDEN`, `404 NOT_FOUND` (no report, target not found, file outside the run), `422` (role, comment, target), `502 LLM_INVALID_OUTPUT`.

## 8. Gotchas

- `ValidationReport.json` is shared: use `latest("SemanticModel")`, `latest("Report")` or `runs_of(...)`, never `runs[-1]`.
- The report hash ignores `renders/`; a diff of two versions needs `renders` skipped.
- The repo uses CRLF in the working tree (`core.autocrlf=true`). `.claude/MANUAL_TESTING.md` is CRLF with a few lone CRs: a rewrite that normalizes endings shows up as a whole-file diff. Edit with exact string replacement that preserves the endings and check `git diff --stat` before committing.
- Bash heredocs with awkward quoting failed several times: write a Python or script file and run it. A tool call times out at about two minutes, so run the offline scripts one per call.
- A visual's PBIR query roles and the plan's roles differ (see `ROLES` in `pbir_generator.py`); adding a visual type needs `ROLES`, the planner schema and `VISUAL_TYPES`.
- Fixed values: `MAX_VISUALS_PER_PAGE = 8`, `MAX_QUERY_ROWS = 100`, planner/regeneration attempts `2`, repair attempts `3` (`config/repair_policy.yaml`).
