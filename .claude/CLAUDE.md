# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Nexora is the AI engine behind a UI called "Rayfin" (`APP_NAME` / `UI_APP_NAME` in `app/config.py`). Both are being redeveloped to run entirely on Microsoft Fabric (see the next section). It takes a business requirement in plain English and works out which tables and columns in a Microsoft Fabric Lakehouse can satisfy it. The sample data is AdventureWorks-style (`saleslt` schema).

## Target hosting: Microsoft Fabric (redevelopment in progress)

**Decided on 2026-10-21:** Nexora and Rayfin are being redeveloped to run **entirely on Microsoft Fabric**. The design is in `.claude/technical-documentation/fabric-hosting.md`, and the operation-to-host map is in `.claude/tasks/CONTRACTS.md#fabric-operations`. In short:
- **UI:** Rayfin becomes a Fabric workload (Extensibility Toolkit) in `rayfin-workload/`, with item type **Nexora Run**.
- **Operations:** short operations are User Data Functions (`nexora_api`). Long, model, data or Fabric operations are notebook jobs (`nexora_stage_runner`), both over one dispatcher (`app/fabric/dispatch.py`).
- **Storage:** run manifests go in the Fabric SQL Database `nexora_control_db`, and every other run file in OneLake `Files/runs/<run_id>/` of the Lakehouse `nexora_control` (through an `ArtifactStore`).
- **Settings and secrets:** settings come from the Variable library `nexora_settings`, secrets from Key Vault through `notebookutils`.
- **Identity:** the Fabric sign-in. Jobs act as the user with `notebookutils` tokens, so there is no OBO.
- **Telemetry:** an Eventhouse.
- **Packaging:** the `nexora` wheel in the Environment `nexora_env`, deployed by `python -m app.tools.deploy_home` (T-005).

**M0, M1 and M7's T-701-T-705 are built (M7's T-706 has no code to write — see its own section); the rest is not.** The rest of this file describes the code as it is today, the first build that runs locally (FastAPI, Next.js `rayfin-ui/`, `.env`, MSAL/OBO, local `runs/`), except for the M0 baseline (see "Baseline (M0)" below), M1 (see "Foundation (M1)" below) and M7's T-701 to T-705 (see their own sections), which are Fabric-aware. ## Baseline (M0)

`app/runtime.py` detects the process once: `RUNTIME` is `"fabric_udf"` when `fabric.functions` is importable, `"fabric_job"` when `notebookutils` is (and `fabric.functions` isn't), else `"local"`. No other module probes the environment; they import `RUNTIME`.

`app/config.py` resolves every setting in this order, first non-blank value wins: the process environment, the Variable library `nexora_settings` (read once per process through `notebookutils.variableLibrary.getLibrary(...)`, Fabric only), then `.env` (local only, loaded once from `PROJECT_ROOT`). `get_required_setting`/`get_optional_setting` are unchanged in shape; `setting_source(name)` reports where a resolved setting came from (`"environment"`, `"nexora_settings"` or `".env"`, never the value) and `required_setting_names()` lists the three `AZURE_OPENAI_*` settings. Those three are **not** required at `app.config` import time in any runtime any more — `app/llm/client.py` requires them again at its own import, so a User Data Function (which must never call the model) is unaffected as long as it never imports `app.llm.client` or anything that does. `AZURE_OPENAI_API_KEY` still goes through Key Vault via `app/security/secrets.py` when `KEY_VAULT_URL` is set (T-705); as an interim rule until T-705 finishes, a development job (`RUNTIME == "fabric_job"` and `ENVIRONMENT == "development"`) may read it from the Variable library when Key Vault and the environment don't have it. New settings: `NEXORA_HOME_WORKSPACE_ID`, `NEXORA_CONTROL_LAKEHOUSE_ID`, `NEXORA_STAGE_RUNNER_ID` (written by `deploy_home`), `RUN_STORE`, `FABRIC_CONTROL_DB_SERVER`, `FABRIC_CONTROL_DB_NAME` (all previously read ad hoc; now proper `app.config` constants too).

`app/auth.py`'s `get_token(scope)` branches on `RUNTIME`: `local` keeps the original shared `InteractiveBrowserCredential` with its on-disk cache; `fabric_job` calls `notebookutils.credentials.getToken(audience)` (scope-to-audience mapping and a 5-minutes-before-expiry cache in `_JOB_AUDIENCE_BY_SCOPE`/`_job_token_cache`; a failure raises `ConsentRequired`, never the token) — see `fabric-hosting.md`'s platform-limits table for which audience each scope maps to, and its caveats; `fabric_udf` always raises `RuntimeError`. `get_credential()` is local-only (raises `RuntimeError` otherwise); `current_identity()` returns the job's user (`{oid, upn, name}`, best-effort from `notebookutils.runtime.context`) or `None` outside a job. No connector signature changed — they already took an optional `token_provider` defaulting to `get_token(SCOPE)`. `FabricSQLConnector` now picks `pyodbc` (ODBC Driver 18) or falls back to `mssql_python` at connect time (`_select_driver()`); `app/connectors/onelake_files.py` is a minimal OneLake Files (ADLS Gen2) read/write/delete helper for small control-plane files, used by the smoke check and `deploy_home` — it is not the T-101 `ArtifactStore`.

`python -m app.tools.smoke` (`app/tools/smoke.py`) gained `control` (a `SELECT 1` on the control database plus a temp-file write/delete under `Files/runs/_smoke/` of `nexora_control`; skipped when `RUN_STORE=file`) and `settings` (every `required_setting_names()` entry resolves, reported with its source) checks, and a `skip` status alongside `pass`/`fail`. `run_checks()`/`run_job()` are the shared, job-callable entry points; `fabric/nexora_stage_runner.Notebook/notebook-content.ipynb` calls them with `operation = "smoke"`, and (T-102) anything else through `app.fabric.job.run_job`.

`python -m app.tools.package` builds the `nexora` wheel (`pyproject.toml`, dependencies read from `requirements.txt` via `dynamic`), versioned `0.<git commit count>.0+<short sha>` or `0.0.0+nogit` outside a git repository (this repo currently has no `.git`), copies `config/*.yaml` into `build/config/` and writes `build/manifest.json`. `SOURCE_DATE_EPOCH` is pinned (to the HEAD commit time, or 1980-01-01 outside git — the ZIP format's own floor) so two builds of the same source produce the same wheel hash.

`python -m app.tools.deploy_home --env dev|test|prod [--create NAME] [--dry-run]` creates or updates the seven home-workspace items (`fabric/` holds the committed Git-format definitions for the Notebook, UserDataFunctions and VariableLibrary items; the others — Environment, Lakehouse, SQLDatabase, Eventhouse — are created bare, since they have no meaningful Git-trackable content yet) through new `FabricItemsClient` methods (`create_workspace`, `get_workspace`, `upsert_item` with create/update/unchanged detection by definition hash, `upload_environment_library`, `publish_environment`). It resolves each item's id, writes the Fabric-specific ones into `nexora_settings`' value set for `--env`, uploads and publishes the wheel (only when its hash changed since the last `build/manifest.json`), and publishes `config/*.yaml` to `Files/config/` of `nexora_control` via `onelake_files`. The exact Git-definition payload shapes for `UserDataFunctions` and `VariableLibrary` are a best-effort reconstruction from public docs (recorded in `fabric-hosting.md`), not yet confirmed against a live tenant — that confirmation is this task's own manual test; T-102 adds the real `nexora_api` code (`function-app.py`) to the `UserDataFunctions` definition payload, with the same caveat.

## Foundation (M1)

`app/store/artifacts.py` is the `ArtifactStore` (T-101 FR-3): every run file other than `RunManifest.json` goes through `read_bytes`/`write_atomic`/`append_line`/`exists`/`list`/`copy_tree`/`local_path`, raising `NotFound`. `LocalArtifactStore(root)` is the local folder (as the first build used it directly); `OneLakeArtifactStore(workspace_id, lakehouse_id)` uses the OneLake DFS API (`app/connectors/onelake_files.py`, which gained `create_if_absent` and `list_files`), not yet run against a live tenant. `get_artifact_store()` (`app/store/factory.py`) picks one from `ARTIFACT_STORE=local|onelake`. **Not done in M1:** the existing stage services still read and write through a local `Path` (`app.fabric.deps.runs_root()`) instead of this interface — see the prominent note in "Target hosting" above.

`app/store/lease.py` is the run lease (T-101 FR-6): `FileLease` (a lock file, exclusive create, JSON `{owner, token, expires_at}`, takeover past expiry, logged) backs both `FileRunStore.lease/release` and `LocalArtifactStore`'s own internal per-call locking (same root, so they coordinate); `SqlRunStore.lease/release` is a conditional `UPDATE` on new `lease_owner`/`lease_expires_at` columns of `dbo.nexora_runs` (migrated in with `ALTER TABLE … IF COL_LENGTH(...) IS NULL`, so an existing table upgrades in place). `LeaseBusy` (re-exported from `app.store.base`) is raised after waiting up to 30 s. `Run` gained `active_job: ActiveJob | None` (`job_id`, `operation`, `job_instance_id`, `status`, `started_at`, `finished_at`, `error`, `reserved_by`); `SqlRunStore` mirrors it into an `active_job` column on `save()`. `python -m app.cli runs pull RUN_ID [--to DIR]` copies a run's files from the artifact store to a local folder (`app/store/pull.py`); `contract validate`/`plan validate`/`report validate`/`model generate` resolve a `runs/<id>` argument through the artifact store (downloading to a temp folder first) when it isn't already a real local directory, via `cli.py:_resolved_run_folder`.

`app/fabric/` is the dispatcher (T-102), framework-free so both hosts can use it:
- `dispatch.py`: `OPERATIONS` is the one table from CONTRACTS.md#fabric-operations (49 entries), matched by method and a `{param}`-style path pattern (`{path:path}` captures the rest, for `GET /runs/{id}/files/{path}`). `dispatch(method, path, query, body, principal, *, as_job) -> {"status", "body", "headers"}` authorizes (`_authorize`: the run's owner, or — inside a job only, since a UDF has no user-delegated Fabric token — whoever Fabric lists the scope workspace for; otherwise `403 ACCESS_CHECK_REQUIRED` from a UDF so the UI knows to retry as a job, full T-705 caching still to come), parses the body against the same pydantic models as before, calls the stage service, and maps exceptions through `errors.py`. A `job:` operation (or `POST /runs/{id}/approvals` with `action: REGENERATE`, whose host is computed from the body) called with `as_job=False` is `400 BAD_REQUEST`.
- `errors.py`: `map_exception(exc) -> {"status", "body", "headers"}`, the first build's `app/api/errors.py` mapping carried over 1:1 (same order, so a subclass like `FabricForbidden` is matched before `FabricError`) plus `RUN_BUSY` (`LeaseBusy`) and `CONSENT_REQUIRED` (`app.auth.ConsentRequired`). `ApiError(status, code, message, details, headers)` is how dispatcher-level failures (bad path, validation, host mismatch, authorization) carry their envelope.
- `schemas.py`: the first build's `app/api/schemas.py` moved here verbatim (`RunDetail` now carries `active_job`, and `next_action` comes from `app.workflow.next_action.next_action_for(run)`, which is `"Wait for <operation label>"` while a job is queued or running); `app/api/schemas.py` is now a two-line re-export so the local FastAPI app is unaffected.
- `deps.py`: what each stage service needs, built with no OBO at all — every connector and client already defaults its `token_provider` to `app.auth.get_token(SCOPE)` (T-002), which is a job's own user through `notebookutils` or the local interactive credential; `set_store_override`/`store()` use a `contextvars.ContextVar` so `nexora_api` (which has no token at all) can swap in a `SqlRunStore` built from its own Manage Connections binding for the duration of one invocation.
- `identity.py`: `principal_from_udf_context(ctx)` reads `fabric.functions.UserDataFunctionContext.executing_user` (`Oid`, `TenantId`, `PreferredUsername` — there is no UPN field, confirmed against Microsoft's docs; see fabric-hosting.md) defensively (dict or attribute access, `None` on anything unrecognized, never raises); `principal_from_job()` is `app.auth.current_identity()`.
- `job.py`: `reserve_job(store, run_id, operation, body, principal)` takes `active_job` (`queued`, `reserved_by` = the UDF caller), `409 RUN_BUSY` if one is already active. `run_job(job_id, run_id, operation, payload)` is what the notebook calls: compares its own identity (`principal_from_job`) against `reserved_by` (T-105 FR-3; a mismatch is `403 FORBIDDEN` and **writes nothing**, so the reservation just expires), then takes the run's lease, dispatches `as_job=True`, writes `runs/<id>/jobs/<job_id>.json` and settles `active_job` to `succeeded`/`failed` — never raises; an unexpected exception becomes a mapped error result instead. `reconcile_active_job(store, run)` is the "whenever the run is read" check (FR-7), called from `_authorize`: a reservation with no `job_instance_id` after 10 minutes becomes `cancelled`; one with an instance id but no result file is checked against `FabricApiClient.get_job_instance` (new method) and becomes `failed`/`JOB_FAILED` if Fabric reports it finished.
- `fabric/nexora_api/function-app.py`: the UDF's real code (`call`, `me`; `@udf.connection(argName="controlDb", alias="nexora_control_db")` + `@udf.context(argName="udfContext")`), thin wrappers over `dispatch()` with no business logic. A one-time manual step (not Git-trackable) adds that Manage Connections binding in the portal after the item is deployed.
- `fabric/nexora_stage_runner.Notebook/notebook-content.ipynb`: `operation = "smoke"` still runs `app.tools.smoke`; anything else calls `app.fabric.job.run_job(job_id, run_id, operation, args)`.

T-103 (scope job, pickers) needed no backend code: `PUT /runs/{id}/scope` was already `bind_scope` (unchanged) behind the `job:` host in the dispatcher table, and the pickers are UI-only (`rayfin-workload/src/lib/fabricRest.ts`, direct Fabric REST with the workload host's token — "the pickers' result is never trusted, the job decides").

`rayfin-workload/` is the Fabric workload (T-104), replacing `rayfin-ui/` (which stays as reference until T-703). It was built against Microsoft's public Extensibility Toolkit docs, not the real Starter-Kit repository (not available to check out here) — see `rayfin-workload/README.md`'s "What's not included" for exactly what that means (no dev-server/bundler/DevGateway, no tenant/publisher registration) and how to drop this project into the real Starter-Kit. What's real and verified: `src/lib/*.ts` (the display-rule libraries, ported unchanged from `rayfin-ui/src/lib/`, same 60 tests passing — `npm test`), `src/lib/api.ts` (rewritten: `call`/`me` invoke `nexora_api`'s published function URLs, `runJob` reserves+starts+polls+reads a job), `src/pages/{RunsListPage,NewRunPage,RunDetailPage}.tsx` (router-agnostic, take a `navigate` callback), and `src/items/NexoraRunItem/` (the item's 4-file pattern, storing only `{runId}`). `npm run typecheck` and `npm test` both pass clean.

T-105 (identity): no MSAL anywhere in `rayfin-workload` (`FabricHostClient.acquireAccessToken`, a documented stand-in for the Workload Client's real token API, is the only way the frontend gets a token); `nexora_api` refuses a call with no UDF context (`401 UNAUTHENTICATED`) except `GET /health`; `run_job`'s reserved-by check is FR-3. **Deferred, same reasoning as T-102 FR-6:** `app/api/security.py`, `app/api/obo.py` and the `ENTRA_API_*`/`NEXT_PUBLIC_ENTRA_*` settings are not removed yet, since `app/api/` itself is kept as a local-dev fallback.

## Spec and design docs

The target product is defined in `.claude/spec/` (requirements FR/NFR, business rules, acceptance scenarios) and `.claude/technical-documentation/` (architecture, artifact contracts, run states, gates G1–G6, milestones, open decisions). Both are transcribed from `Nexora_Specification_and_Technical_Design.docx` (v0.1 draft). Read them before adding a new pipeline stage.

The real stages are in `app/compiler/`, `app/discovery/`, `app/model/`, `app/report/`, `app/repair/` and `app/workflow/`.

Manual test steps for every finished task are in `.claude/MANUAL_TESTING.md`; `/implement-task` updates it at each hand-over. Hand-over notes of the sessions that built the tasks (state, working rules, what each task built, gotchas, open follow-ups) are in `.claude/session-context/`, one file per session named `T-<first>-to-T-<last>.md` (T-001 to T-005, T-101 to T-202, T-203 to T-205, T-301 to T-304, T-401 to T-405, T-501 to T-507, T-601 to T-604, T-701 to T-706): when you work on or review one of those tasks, read the file that covers it first. T-001 to T-005 and T-701 to T-706 describe Fabric-native sessions; the rest describe the first, locally hosted build, with a later Fabric rework section at the top where one exists. For the Fabric rework, the task file and `fabric-hosting.md` win over them. The code and this file win if they disagree.

The human workflow (dev session `T-xxx` plus review session `T-xxx_test`, task branch, PR, cleanup) is described in `.claude/DEVELOPMENT_WORKFLOW.md`. In a `_test` session, review and help test only; don't implement the task. Use `/review-task [T-xxx]` (`.claude/skills/review-task/SKILL.md`) for the review. The build order is in `.claude/tasks/` (T-001 … T-706, grouped by milestone M0–M7). Each task has six sections (problem statement, functional requirements, API contracts, constraints, edge cases and error handling, acceptance criteria). Its acceptance criteria must pass a manual test before the next task starts. Shared shapes and error codes are in `.claude/tasks/CONTRACTS.md`; implement against them exactly. `.claude/tasks/README.md` lists the decisions and the defaults assumed for the spec's open decisions: Fabric hosting, hybrid orchestration, the Fabric SQL plus OneLake control store, and so on. Orchestration is decided as **hybrid**: the run state machine and `RunStore` own run state, approvals and audit, and LangGraph stage graphs run only the LLM loops inside a stage (rules in `.claude/tasks/CONTRACTS.md#stage-graphs`). Use `/implement-task <milestone file | task ID>` (`.claude/skills/implement-task/SKILL.md`) to work on a task. It enforces the dependency order and keeps the README status column up to date. Use `/commit-push [branch | "note"]` (`.claude/skills/commit-push/SKILL.md`) to commit with a generated message and push. The repo is public, so that skill blocks secrets and binaries. After a branch's PR is merged, `/cleanup-branch [branch]` updates local `main` from the remote and deletes the branch, after a caution message and confirmation.

Rules from the spec that constrain all new code:
- The LLM proposes; deterministic validators decide progression.
- No silent assumptions for KPI definitions.
- Return "Not Feasible / Data Gap" instead of fabricating a calculation.
- A LangGraph stage graph never changes run state or writes `RunManifest.json`. Its loops are bounded, and it routes only on validator output. In Fabric it runs only inside a notebook job, never in a User Data Function.
- Fabric rework: UDF and job handlers hold no business logic (they call the dispatcher). Model calls and source, Fabric or Power BI access happen only in jobs. Nothing writes outside Nexora's control items and the sandbox, except the promotion job (T-702).

- Test data for the acceptance scenarios lives in schema `nexora_test` of the sandbox Lakehouse. It is created by the Spark notebook `fixtures/create_test_tables.ipynb` (see `fixtures/README.md`), not by Python in `app/`. `python -m app.test_metadata_inventory [schema]` lists a schema's tables (default `saleslt`).
- There is no build, lint, or pytest setup. The `app/test_*.py` files are **manual scripts** with a `main()`. Each exercises one pipeline stage against live Azure/Fabric.
- Run them as modules from the project root (`python -m app.test_x`). Imports are absolute (`from app.config import ...`), so running the file directly will fail.
- Running anything locally needs a `.env` (copy `.env.example`; with `KEY_VAULT_URL` set the model key and the API client secret come from Key Vault instead, T-705). `app/config.py` resolves settings from the process environment, then the Variable library `nexora_settings` (Fabric only), then `.env` (local only, loaded once from `PROJECT_ROOT`). `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_DEPLOYMENT` and `AZURE_OPENAI_API_KEY` are optional in `app.config` itself (a User Data Function must never call the model, see "Baseline (M0)"); `app/llm/client.py` requires them again at its own import, so importing it (every real model call does) raises `ValueError` if any is missing. The Fabric settings (`FABRIC_*`) are optional: `get_optional_setting` returns `None` when they are unset or blank.
- Fabric access goes through `app/auth.py`'s single `get_token(scope)`, which branches on `app.runtime.RUNTIME` (see "Baseline (M0)"): locally, one process-wide `InteractiveBrowserCredential` with an on-disk token cache (`TokenCachePersistenceOptions(name="nexora")`), plus a saved sign-in record (`%LOCALAPPDATA%\.IdentityService\nexora_auth_record.json`, account identifiers only, no tokens), so a process signs in once and later runs read the cache silently (delete that file to force a fresh sign-in); in a Fabric job, `notebookutils.credentials.getToken`; in a User Data Function, a `RuntimeError`. ## Runs

Any other state, `DEPLOYING` included, is `409 WRONG_STATE` and changes nothing. Once the changed artifact is approved again (`approval.perform` calls `impact.on_accept` after every Accept; a contract counts when its status is `approved`, a ModelSpec when it is) the baseline is compared with the current files at object level: KPIs by name (`formula_intent`, `grain`, `filters`, `time_logic`, `exclusions`, `currency`, `expected_examples`; wording such as the objective or a rationale changes nothing), entities, dimensions and security, and for the ModelSpec its measures, tables, relationships, roles and storage mode. The dependency map is applied: a changed KPI is stale in SourceResolution, Feasibility and ExecutionPlan (`kpi:<name>`) and in ModelSpec through its measure (`kpi` name), plus every measure whose DAX uses a changed measure; the TMDL model lists those measures and the table files they live in (`file:definition/tables/<Table>.tmdl`, `definition/relationships.tmdl`, `definition/roles/`); the ReportPlan and the report list the visuals that bind a changed measure or a column of a changed table. A different entity, a storage-mode change, an unreadable baseline file or an unreadable plan makes the artifacts stale as a whole (`*`). A deleted KPI's measure, file and visuals are in `removals` and are never dropped silently. Artifacts that were rebuilt since the baseline (a different hash) are not stale. Stale artifacts get `status: stale` (the earlier status is in `Impact.json`).

`workflow/stale.py` holds `StaleArtifacts` (`409 STALE_ARTIFACTS`, `details.stale`) and `assert_fresh`. A stale artifact blocks what builds on it: `apply_transition` refuses `DEPLOYING` (checked before legality), and plan generation, feasibility, plan edits and Accept of the plan, model generation and Accept of the model, report planning and generation and Accept of the report each name the stale artifacts they need.

`POST /runs/{id}/regenerate-stale` (`workflow/regenerate_stale.py`, `regenerate_stale`) returns `{"regenerated": [...], "validation": [...], "needs_review": [...], "run": RunDetail}`. ## Architecture

A staged discovery pipeline. There is no orchestrator or entry point yet; the `test_*.py` scripts wire the stages together by hand. Data flows between stages as plain dicts or the `RequirementSpec` pydantic model:

1. `llm/requirement_analyzer.py` — `analyze_requirement()` returns a `RequirementSpec` (objective, entities, metrics, dimensions, filters, security requirements, assumptions, clarification questions).
2. `connectors/fabric_lakehouse.py` + `discovery/metadata_inventory.py` — `build_metadata_inventory()` returns `{schema_name, tables: [{table_name, columns: [{name, data_type}]}], errors}`. It reads the OneLake table REST API with a bearer token for `storage.azure.com`.
3. `discovery/requirement_data_matcher.py` — deterministic matching of requirement terms to inventory columns, driven by `config/glossary.yaml` (`discovery/glossary.py`) and name normalization.
4. `discovery/semantic_mapper.py` — LLM-suggested mappings and join relationships, given the requirement and the inventory.
5. `discovery/relationship_validator.py` — checks the suggested relationships against the inventory. With `run_data_checks=True` and a connector, it also checks them against real data.
6. `connectors/fabric_sql_connector.py` — a separate read-only path to the Fabric SQL endpoint (pyodbc; passes a `database.windows.net` access token via `attrs_before={1256: ...}`). Used by `discovery/data_profiler.py` and the data checks in step 5.

Design rule stated in the code: **inventory metadata is the source of truth** for which tables and columns exist. LLM output is only a candidate until validated, so don't let LLM-suggested names bypass the validator.

### LLM access

`llm/client.py` builds one shared `OpenAI` client pointed at Azure's v1 endpoint (`{AZURE_OPENAI_ENDPOINT}/openai/v1/`). It uses the Responses API (`client.responses.create`) with `model=AZURE_OPENAI_DEPLOYMENT`. Prompts name the assistant "Nexora"; `ask_rayfin()` is the generic helper. The analyzer and mapper ask for JSON and validate it (pydantic for the analyzer).

## Gotchas

- Table and column names are hardcoded in several places for the sample data (`saleslt.SalesLT_Product`, `saleslt.synthetic_sales_daily`, `data_profiler.py`). Generalizing means touching all of them.
